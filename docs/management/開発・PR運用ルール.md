# 開発・PR運用ルール

## 基本フロー

1作業＝1ブランチ＝原則1PR。開始前にworking treeと進行中PRを確認し、`git fetch origin`でmainを最新化する。ローカルmainがない場合も、最新の`origin/main`から専用feature branchを作れる。

```bash
git fetch origin
git status --short
git switch -c feature/xxx origin/main
```

mainに直接commit / pushしない。専用ブランチで実装し、必要な検証とdiff確認後、対象ファイルを明示してcommit・pushする。PR作成後はCIを確認し、必要なレビュー・修正と再検証を行う。**マージはユーザーが手動で行う。Codexは勝手にマージせず、自動マージも設定しない。**

ユーザーのマージ後は、対象main SHAのCI起動・全job・Pagesデプロイ・公開内容を確認する。必要に応じてリモートとローカルの作業ブランチを削除し、次の作業は再度最新mainから始める。PR時CI成功とマージ後CI・公開成功は別に報告する。

## PR本文

原則として次を日本語で記載する。

- 背景・目的、変更内容、変更対象ファイル
- 既存機能への影響
- テスト・検証結果（実測値、終了コード、CI URL）。未実施なら未実施と理由
- CI種別（軽量／フル）と選択理由
- 既知の制約・未解決事項、後続PRへの引継ぎ

CI待ちを成功と書かない。PR作成後に実測結果で本文を更新する。ラベル付与に失敗した場合も、付与成功や軽量CI成功と報告しない。

## PRを分ける基準

- 目的の異なる変更を混ぜない。大規模変更は必要に応じて調査・設計・実装を分割する。
- 正式設計契約の変更と単なる表記修正を区別し、過去の検証記録を現在の実装に合わせて書き換えない。
- 既存の安全性・データ整合性を維持し、レビュー可能な変更量を優先する。

## CIの選択と確認

詳細は既存の[CI運用ルール](../../.github/CI.md)を正とする。Codexは変更内容から判断し、軽量なら`ci:light`、フルならラベルなしとする。workflowはファイル内容を自動判定しない。

ドキュメント・README・開発ルール・実行コードや正式契約に影響しない表記整理は軽量の候補。ただし正式な安全契約や運用手順を実質的に変える文書変更は個別判断する。JavaScript、canonical CSV、ランキング生成・集計、FN-004 runtime、workflow、テスト、公開HTML/CSS/JavaScript、安全性・データ整合性に影響する変更は原則フル。迷う場合もフルとする。

本書は開発手順を整理するもので、FN-004のProduction Apply / Recovery等の正式操作手順を変更しない。[CLIガイド](FN-004-canonical操作ガイド.md)と正式設計・個別の人間承認を参照する。
