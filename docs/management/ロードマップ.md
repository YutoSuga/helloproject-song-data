## SCR-101：Web管理画面へのArchitecture milestone

現在はCLI / file中心で、FN-004までのruntimeは実装済み。以下は責務の流れ。

```text
official source → FN-002 → song-candidates → FN-003
  → human review / Decision → FN-004 → canonical CSV
  → FN-001（ランキング）/ FN-005（楽曲一覧）→ 共通ビルド・公開 → 公開サイト
```

SCR-101以降の想定は次の役割分担となる。

```text
SCR-101 admin UI → authenticated Backend / API
  → FN-003 / Decision / FN-004（CLIと共通のapplication service）
  → canonical CSV
```

既存の6内部view・共通service境界を基礎に、Web管理画面中心へ移行する大きなArchitecture milestoneとなる。Backend技術、API方式、認証provider / session、hosting / deployment方式は未決定で、今後のArchitecture設計で選定する（旧計画は2026年12月）。browserがGitHub tokenやCSV・lock・journalを直接操作する構成にはしない。公開サイトは静的公開を維持し、bootstrap / recovery実行はv1ではCLIのみとするため、通常運用の管理画面化と障害復旧のCLI運用は両立する。

## JOB-001後の運用イメージ

基本思想は**「収集は自動化、確定は人間」**。

```text
JOB-001の定期実行 → FN-002 candidate collection
  → FN-003によるレビュー準備 → SCR-101で人間確認 → Decision
  → FN-004 canonical apply（Plan / Approval / Request / Transaction）
  → canonical data → FN-001（ランキング）/ FN-005（楽曲一覧）→ 共通ビルド・公開 → 公開サイト
```

JOB-001はFN-002を起動し、判断・canonical反映を自動確定しない。通知は対象外。Apply後のdiff確認・validation・site build・通常commit / push / PRはTransaction外の既存運用を維持し、この図は全工程の無人実行を意味しない。

## 「完成」の定義

旧見積もりの2027年3月の目標はMilestone 3完成、すなわち日常運用可能な管理基盤の完成を意味する。

- 候補収集を自動化できる。
- 人間が管理画面で候補を確認し、Decisionを安全に作成できる。
- FN-004でcanonicalへ安全に反映できる。
- canonicalから公開サイトを更新できる。
- 通常運用を管理画面中心で行える。

その後もデータ拡充、UX改善、新機能、追加分析、新しいofficial source対応、保守などの継続開発を行い得る。Milestone 4や将来拡張までの完了をこの目標には含めない。

## Milestone 1：ランキングカテゴリ拡張

対象：FN-001 公開サイトデータ生成機能 / 公開サイト。

実装済み。曲数ランキングはすべて（`all`）、作詞、作曲、作詞 & 作曲、編曲の順で表示します。

「すべて」は対象artistのprimary音源で作家が担当した作品を全役割から集計します。「作詞 & 作曲」（`lyrics_composition`）は、同じ作家が同じ音源で作詞と作曲の両方を担当した作品を集計します。順位と集計根拠の仕様は[FN-001](../design/functions/FN-001-ランキング集計仕様.md)を参照してください。

## Milestone 2：作詞 × 作曲 組み合わせ分析

対象：FN-001 公開サイトデータ生成機能 / 公開サイト。

実装済み。通常のランキングカテゴリとは別の分析機能として、以下を追加しました。

- 作詞者 × 作曲者の組み合わせランキング
- 同一人物による作詞・作曲の組み合わせも対象
- 共同作詞・共同作曲は全組み合わせを対象
- 同じwork・同じ組み合わせはバージョン違いでも重複カウントしない
- 組み合わせは同じ具体的な`song_id`上のcreditから生成する
- 別version間の作詞者と作曲者を組み合わせない

表示機能として、以下を追加しました。

- 全組み合わせランキング
- 特定Creatorを作詞者として選択し、組んだ作曲者を表示
- 特定Creatorを作曲者として選択し、組んだ作詞者を表示
- 自作詞・自作曲作品数

指定artistがprimaryのsongのみを対象とし、pairごとのwork数と根拠songを派生JSONへ保存します。全組み合わせ・Creator起点の両方向ともcompetition rankingで表示します。詳細は[集計仕様](../design/functions/FN-001-ランキング集計仕様.md)を参照してください。

## Milestone 3：他Hello! Projectグループへの展開

3-A と 3-A Follow-up は完了。FN-002 楽曲候補収集機能はモーニング娘。、アンジュルム、Juice=Juice、つばきファクトリー、BEYOOOOONDS、OCHA NORMA、ロージークロニクルの主要7グループに対応し、実サイトで全対象 artist の収集に成功した。FN-001のランキング処理は特定の `artist_id` をハードコードせず、指定して集計できる構成を維持する。3-B1 / FN-003は完了しており、FN-004はruntime実装・受入済み。今後の順序は上記の合意方針を参照する。

- **3-A / FN-002 楽曲候補収集機能（完了）**：公式 release 一覧・詳細から音声トラックを収集し、正本 CSV と参考照合して `staging/song-candidates.json` に保存する。人間の status と notes を再実行時も保持する。詳細は[収集仕様](../design/functions/FN-002-楽曲候補収集仕様.md)。手動CLIはFN-002の入口であり、定期起動のJOB-001は未実装。
- **3-A Follow-up / FN-002 複数artist収集（完了）**：通常運用は設定済み7グループ全体、個別確認は `--artist <slug>` を使用する。全選択 artist の成功後だけ共通 staging を一度保存し、途中失敗時は更新しない。旧名義・関連ユニットは source と実名義を区別して保持し、artist identity を自動統合しない。
- **3-B0 structure / docs refresh（完了）**：現行構造、実装機能、データフローを README と基本設計に反映し、3-B1 / 3-B2 の入口を整理した。
- **3-B1 / FN-003 レビュー準備機能（完了）**：候補と正本 CSV、過去レビューを照合し、自動で分かる情報と人間判断が必要な項目を `staging/song-reviews.json` に整理する。正本 CSV は書き換えない。
- **3-B2 / FN-004 canonical反映機能（runtime実装済み / Final Acceptance PASS）**：有効confirmed Decisionから不変Planを作り、Approval・request_id付きdurable受付を通して既存参照/新規追加をall-or-nothingに反映する。COMMIT_DECIDED前は原則rollback、後はHistory等をfinalizeする。bootstrap・ID上限・再送/復旧契約を含む。
- **3-C / SCR-101 楽曲管理画面（interface設計済み / runtime未実装）**：管理一覧・レビュー編集・Decision確認・Apply Preflight・Apply結果・System Statusの6内部view。CLIと同じserviceを使い、bootstrap/recovery実行はv1ではCLIのみ。認証/hosting等は別途選定する。
- **3-D / JOB-001 楽曲候補定期収集ジョブ（予定 / 未実装）**：FN-002を定期的に起動する。実装着手時に専用の詳細設計書を追加する。通知は別ジョブとして必要時に定義する。

FN-003の現行schemaとFN-004正式v1設計の入口は[canonical registration](../design/system/レビュー準備・canonical反映の全体フロー.md)。詳細は[Decision](../design/functions/FN-004/10-判断モデル.md)、[Plan](../design/functions/FN-004/20-反映計画.md)、[Transaction](../design/functions/FN-004/40-反映処理・復旧.md)、[共通サービス・CLI契約](../design/system/楽曲管理のアプリケーションサービス・CLI契約.md)を参照する。Slice 1〜6F・CLI実装、Final Acceptance、findingクローズの実績は上表を参照。本番初回Apply・日常運用開始とは区別する。

## Milestone 4：複数artist横断機能

複数グループのデータが揃った段階で検討します。特に以下の仕様を確定する必要があります。

- 同じworkを複数artistが歌っている場合の集計方法
- coverの扱い
- multiple primary artist
- NEXT YOU等の別名義
- temporary / shuffle unit
- solo
- featured artist

Hello! Project全体ランキングなどの横断集計は、これらの仕様確定後に実装します。
