## B・C. 公開データ方針、変更範囲とリスク

- 初回リリースでは2種類の既存JSONとその他のJSONを読み、共通取得と画面内派生だけを追加する。ホーム・ランキング・作家検索はランキング、楽曲検索・詳細・作家指定分析は楽曲、作家詳細は両方を取得。分析の組み合わせタブはランキングのみで一覧と作品リンクを描画できる。検索・分析は表示タブに必要なデータを取得し、artist別・データ種別ごとに成功した読み込みを同一ページで再利用する。両JSONを読む作家詳細ではartistと参照Work IDを検証する。missing entryを0件と混同しない。
- 現在のデータ量なら作家指定分析は選択作家ごとにSongのクレジットを走査できる。複数artistの公開は将来、現行ジェネレーターへIDを渡し、公開リストと両JSONをセットで更新する。対応artist増加でbuild/validatorを広げるなら同じ一覧を全工程で参照し、各artistについて生成・独立検証・再生成差分検査を行う。作品別シェア画像や分析データの事前生成は、個別OGPが必要、または実測で読み込みや応答時間に問題が出た場合に再検討する。その場合は派生JSONの分割・別ファイル追加を先に検討し、既存reader契約、出力追跡、GitHub Pages artifactを維持する。
- `date_incomplete`は既存契約にある。楽曲詳細で参照を始めるためreaderの検査を追加する。型・意味とschema_versionは維持。同一Song上の支持クレジットは楽曲JSONで確認し、ランキングのWork集約rolesで共担を推定しない。
- その他の本文と公開更新履歴（`site/data/about/updates.json`）は実装・公開時に更新。必要に応じpolicy/coverageに旧称・誤導線がないか確認する。ID、データ収録範囲、正本、動画関連CSV、FN-004およびProduction Bootstrapのコード・保存資産・検証境界は維持する。

## D. 実装順序、PR分割、受入条件

設計のレビュー後、公開サイト再構成を **実装1 PR** にまとめる。新ナビ・互換リンク・状態共有・相互リンクを同じPages artifactで切り替えれば、前後の別リリースに依存するリンクが残らない。レビューしやすい順にコミットを分ける。

| 実装順 | コミット範囲 | 受入条件 |
| --- | --- | --- |
| 1 | 共通シェル・URL/履歴・公開データの読み込み、互換ページの骨組み | 5ナビ・ブランド・metadata・正規URLが共通。URL優先・再訪・無効値・ストレージ障害、詳細の必須ID、全旧URL、動画直アクセスを検証 |
| 2 | ホーム・順位・検索・その他 | 順序とショートカット、同順位を含むTOP3、基点集計との一致。作家検索の並びと楽曲の検索・3順序を回帰検証。その他の既存アンカーと履歴を確認 |
| 3 | Work詳細・作家詳細・分析・根拠表示 | 1音源/複数音源のクレジット、相互リンク、作家指定分析へ直行、共担の根拠、既存pairフィルタと自己pair、復帰を検証 |
| 4 | 統合回帰・受入・公開準備 | 下記テストを通し、基点の生成JSONと順位が一致し、変更が正本・管理に及ばない。最新mainと最終CIを確認して人がマージ判断 |

PR分割は、公開データ契約変更が必要になって独立レビューが必要な場合、または分析の検証に時間がかかり一括受入が困難と判明した場合のみ再検討する。前者は後方互換の生成契約・生成検証を先行（公開導線・旧reader維持）、後者は先行PRで移行と組み合わせランキングまで公開し、作家指定分析とそこへのリンクを後続PRで同時に有効化する。中間公開が仕様と異なるため後者はユーザー同意を前提とする。

### 実装PRの検証

- 通常CIの `npm test`、canonical全14テーブル検証、最新main基準のID検証、ランキングと楽曲の独立検証、build、生成差分、`git diff --check`。生成データのハッシュと順位・根拠の比較。CIのPages deployはmainのみ。
- 集計モデルは同順位 `1, 2, 3, 3` と `1, 2, 2, 4`、featured/multiple-primary、同一Songの複数役割・同一役割の共担、Songをまたぐだけのケース、同じWork内で複数成立、自己pair、credit空、日付欠損、候補なしをfixtureで検証する。
- ブラウザでPC/SP（320/390/768/1024/1440px）の全ルート、キーボード（タブ、コンボ、IME、Escape、dialogのTab/Shift+Tab）、長い名前、固定UI、横はみ出し、空/取得中/失敗、直接アクセス、クエリ・アンカーのリロード、戻る/進む、別タブ、旧URL、保存不能を検証。公開2artistのfixtureで切替・保存優先順位・リクエスト競合も確認する。
- main上の公開後は主要経路と旧URLのHTTP・表示、実際に取得されるHTMLのメタタグ、データファイル、SP表示を確認する。万一rollbackが必要なら、公開変更のPRを単位に通常のrevert PRを作る。正本のデータ変更を巻き戻さない。

## E. 判断事項

| 判断事項・技術制約 | 推奨案 | 代替案・影響 |
| --- | --- | --- |
| 作家指定分析の「共同制作」 | 同一Songの全役割・別作家、Work重複排除。既存pairとの差を集計方法で説明 | Workだけ共有する別音源まで含めると実際の共通クレジットがなくても加算される。作詞×作曲限定では編曲・共担を取りこぼす |
| 休止URL（現行は準備中画面） | 200の休止案内＋noindex。既存URLから戻れる | ファイル削除の真の404。静的Pagesでパス別410は通常設定できない |
| 詳細の個別OGP | 初回は静的な共有メタデータとブラウザの個別title。クエリ型詳細はnoindex | 共有サービスがJSを評価しないため、個別プレビューが必要ならWork/creatorパスの静的生成を別途設計 |
| OGP画像・アイコン | 既存アイコンを点検し、共有画像はブランド確認後に決定 | 新規ブランド画像を実装PRに含める場合はそのデザインもレビュー |
| 作家分析の実装位置 | 既存JSONをブラウザで利用。公開アーティスト追加まではG00001のみ選択可 | 大規模化して遅延が出た場合のみ派生JSONの事前生成を再評価 |

要確認は共同制作定義、動画旧URLの休止応答、個別OGPの初回要否、共有画像の扱い。合意済みの画面・集計を変更する前提はない。明示されていた「担当区分の切り替え」は現行pairで提供する作家選択＋作詞／作曲チェックを指す設計とし、編曲組み合わせの新規集計は追加しない。
