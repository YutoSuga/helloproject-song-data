# FN-004 Validation / Transaction / Recovery

正式v1設計。Slice 1〜3の読込/排他/bootstrap基盤は実装済み、実Apply/Transaction/Recoveryは未実装。[全体設計](レビュー準備・canonical反映の全体フロー.md)、[Decision](FN-004-判断モデル.md)、[Plan](FN-004-反映計画.md)、[Approval / durable Request](楽曲管理のCLI・画面連携.md)を参照する。

## 保証範囲

Node.js 20以降、単一authoritative working tree、協調するreader / writer、同一のローカルfilesystemを対象とする。file sync・directory sync・同filesystem rename・排他的な新規file公開が機能するprofileを必須とする。未対応ならwriteをSTOPする。NFS等の共有filesystem、複数cloneの同時採番、Gitによる台帳巻戻しはv1運用対象外。状態を戻したcheckoutや分岐した台帳を認識した場合は再照合前にApplyしない。

複数CSVへ単一のOS atomic rename transactionはない。共通gateで途中状態を隔離し、未完了処理があれば通常利用を止め、original復元またはtarget完了を保証する論理的all-or-nothingとする。非協調editor・hardware故障・flushを無視するstorageまで含めた絶対保証はしない。

既存FN-003 / collectorのtemp＋renameは単一JSON保存で、fsync・複数表journal・recoveryを実装していない。`src/canonical.js`はranking用読込、`src/prepare-reviews.js`の検証も全仕様を網羅しない。本設計の安全保証を現実装済みと扱わない。

## 受付とtransactionの境界

順序は**Approval保存 → durable Apply Request受付 → transaction journal開始**。Approvalなしの実行要求を受け付けない。完全schema・approval_hash/request_payload_hash/receipt_hash projectionは[Hash Contract](FN-004-承認・反映リクエスト.md)、受付とidempotency lifecycleは[interface設計](楽曲管理のCLI・画面連携.md)を正とする。receipt hashは外側schema_versionとreceiptのwrapperを対象とし、processing cacheを含めない。元receiptのrequested_at/transaction_id/apply_idは同request retryで再生成しない。

receipt保存は短い受付gate内で行い、transactionの実行排他とは責務を分ける。同一gateを継続保持する実装も可。新規受付前にlock・unfinished journal・未完了receipt・ID pendingを確認し、他要求があればBUSY / RECOVERY_REQUIRED。受付後gateを解放しても未完了receiptが次の新規受付を阻止するためqueueや複数claimは生じない。

同request再送は既存状態を返すだけで、新transactionをdispatchしない。初回受付者だけがreceiptに固定したtransaction_idで実行へ進む。receipt公開後にprocessが終了した場合はrecoveryで元要求を終了させる。journal不存在だけで未開始と断定せず、ID state・History・canonical・owner・残存artifactを検証する。実行/recovery内部の読込は、所有gate leaseと期待する本人request/pendingをcontextに含める。本人の期待遷移だけを認め、他要求や通常readerにpending検査の迂回optionを公開しない。

Approvalの現在の新規利用可否と、受付時のexact bindingは[Approval Invalidation Contract v1](FN-004-承認・反映リクエスト.md#approval-invalidation-contract-v1)で区別する。受付後eventは元Receiptへのaccepted_request参照で検証し、それだけで既存Requestのexecution/Recoveryを取消し・拒否・rollbackしない。受付前event（accepted_request=null）と同Approvalのreceipt共存はINTEGRITY_CONFLICT。これはexecution再検証における承認の解釈であり、COMMIT_DECIDED、journal、History成功、high-waterの規則を変更しない。

## exclusive gate・stale lock

realpathでrepository rootを確定し、`staging/.fn004.lock`を`fs.open(path, "wx")`で取得する。schema、owner token UUID、mode、PID・process開始識別子、host / boot / PID namespace、root、request / transaction / apply / Plan identity、取得時刻、journal pathを保存・syncする。EEXISTはBUSY。途中で切れたmetadataも無条件削除しない。

FN-001 / FN-003 / collector等のcanonical読込は、snapshot読込全体で同じgateを取得する。Decision・candidate等の更新も協調させる。存在確認を一度するだけではTOCTOUを防げない。readerは未完了journal / request / ID pendingがあれば通常読込を止める。既存readerの共通化はFN-004実装の前提である。独立したcommit済みcheckoutで動くPages buildは元working treeの途中状態を読まない。

通常Applyはstale lockを削除しない。PID不存在・経過時間だけで解除しない。recoveryは`staging/.fn004-recovery.lock`をexclusive取得し、元ownerが同host / boot / namespaceで確実に終了したか、owner token・journal・実hashを照合する。元lockを空けずにownerを移管し、recovery完了後だけ解除する。別host、PID再利用、recovery mutex自体の不明状態は人間確認でSTOP。自動takeoverできる証拠がなければforce optionでも進めない。

## execution・validation

1. execution gate取得、他の未完了処理不存在、本人receipt / Approvalを確認。
2. Plan schema/id/hash/rules、承認hash、Decision identity/hash/有効confirmed、candidate fingerprint、全14表manifest、History、ID state、planned ID可用性を再計算。
3. reuse row・no_op全列一致・insert不存在・conflict/unsupportedなしを確認。staleならCSVへ触らずrequestをterminal拒否とする。
4. original全14表を同じバイトsnapshotから検証し、PREPARINGを記録。
5. apply_timeを一度固定し、Plan＋originalからtarget全体をメモリ生成。全検証・target manifest計算。
6. 全14 CSV backup、changed CSV temp、Plan・Decision・Approval・Requestの検証済みcopy、intentを保存してsync。tempを再読込して検証。
7. 全preconditionを最初の置換前に再確認し、PREPARED → COMMITTINGをdurable記録。
8. ID消費・pendingを永続化してからchanged CSVを固定順で置換。
9. 全14表を実pathから再読込しwhole validation・target manifest一致を確認。
10. COMMIT_DECIDEDをdurable記録。History公開 → ID state成功head → COMPLETED → request結果参照整合 → unlock。

`apply_time`はtarget生成前のPREPARINGで固定し、全new masterのcreated_at / updated_atへ同値を入れる。recoveryで変更しない。`applied_at`はCOMMIT_DECIDEDの成功確定時刻として固定する。確定後の再試行でHistory内容を変えない。

### whole canonical validator

全14表について正確なheader / 列順・UTF-8・CSV構文・列数・必須値・PK・ID・FK・enum・実在日付・timezone付き日時・HTTPS source・正整数/非負整数・order一意性を検査する。song primary、期間start/end、member affiliationの同一member/artist期間重複、videoのYouTube ID/URL一意・区間複合FKも対象。CSVの引用規則はデータ仕様に従い、既存parserの寛容な受理だけでvalidとみなさない。

original、メモリtarget、temp再読込、commit後で検証する。既存rowの値・timestamp不変、削除なし、許可tableへのinsertだけかも検証する。original判定例外・音源同一性等は人間根拠を検査し、推測で再判断しない。意味的制約の検査をwarningだけに落とさない。

### Slice 1 runtime API（読み取り基盤のみ）

- [`canonical-schema.js`](../../src/canonical-schema.js) の `CANONICAL_TABLES` / `CANONICAL_SCHEMA` が14表の列順、必須性、型、PK/FK、enum、order/期間等のruntime契約。`CANONICAL_SCHEMA_VERSION = 1`。FN-003もこのmetadataを参照するが、既存の部分検証・reader APIは維持する。
- [`canonical-validator.js`](../../src/canonical-validator.js) の `validateCanonicalTables(tables)` は全14表のrow配列を受けるpure function。rowは全列をCSV文字列で保持し、未確認の任意値は空文字。整数は全fieldを検査し、比較keyを任意精度で正規化する。`ok, diagnostics`を返し、processを終了せず入力を変更しない。header検査はsnapshot読込側が担う。
- [`canonical-snapshot.js`](../../src/canonical-snapshot.js) の `readCanonicalSnapshot(root)` はrepository rootから各fileを一度読み、同じBufferを厳密UTF-8 decode・共通CSV parserのstrict mode・hashに使う。戻り値は `{rawBytes, tables, manifest, validation: {ok, diagnostics}}`。rawBytesはPOSIX pathをkeyとするBuffer、tablesはtable名をkeyとするrow配列。返却値はcallerが読み取り専用として扱う。
- manifestは `{schema_version: 1, files, manifest_hash}`。filesの各entryは `{path, byte_length, sha256}`、path ASCII昇順。hashは[Plan設計](FN-004-反映計画.md)どおり **SHA-256(JCS(files))** であり、schema_versionやmanifest_hashをhash対象へ追加しない。個別hashはCSVの生bytes、hexは小文字64桁。共通の [`canonical-hash.js`](../../src/canonical-hash.js) がRFC 8785のJSON canonicalizationとSHA-256を提供する。
- file欠落・読込不能・未知CSVでは完全manifestを返さずnull。CSV内容がinvalidでも読めたbytesのmanifestは取得できるが、`validation.ok=false`なら利用可能canonicalとはみなさない。診断はerror severity、安定code、file/table、該当時record番号/column/key、messageを持つ。row番号はheaderを1とする論理CSV record番号（引用内改行は同record）。未来releaseやoptional notes欠如は正常。
- Slice 1にはgateがない。複数fileの読込中に外部変更されない保証はなく、**後続sliceが共通gate下で呼ぶ必要がある**。hash用とparse用の再読込は行わない。CSV書込、diff、既存値変更禁止の比較、serializer、transaction/recovery、ID採番、CLIは未実装。

### serializer rule v1

Planがbindingするserializer=1は、変更するCSVをUTF-8/BOMなし、canonical schemaのheader/列順、record区切りLF、最終LFありで出力する。カンマ・CR・LF・二重引用符を含むfieldだけを二重引用符で囲み、内部引用符を二重化する。field内の文字/改行は無変換。既存rowは元の順序・全field値を維持し、新insertをtyped PK順で末尾へ追加する。非変更fileはbytesごと不変、変更fileの既存fieldのquote表現だけが再serializationで変わり得る。raw manifestはそれも含めtargetとして検証する。Plan生成でCSVを書かず、system apply_timeの実値とtarget bytesは実Transactionだけが決める。

## directory・durability

### Slice 2 runtime API（repository / persistence / gate）

- [`fn004-gate.js`](../../src/fn004-gate.js) の `acquireGate` / `releaseGate` / `withCanonicalGate` がread/write共通のexclusive leaseを扱う。rootはrealpath、lockは`staging/.fn004.lock`の`open("wx")`。schema_version=1、lock_id UUID、PID、operation/mode、開始時刻、caller、host、platform、process identityをfile sync・directory syncして保持する。Linuxではboot ID・PID namespace・process start ticksも記録し、取得不能なOS情報はnull。repository UUIDは発行しない。
- releaseはprocess内WeakMapに登録されたlive token、fileのdev/ino、metadataの全bytesを照合する。serialized/copied tokenは無効。callback例外でもreleaseするが、ownership不明ならunlinkしない。release/sync失敗は`GATE_RELEASE_FAILED`等とcleanup_requiredを返し、本体例外があればoperation_errorに保持する。crash後lock、古いPID/時刻、空・破損・未知version・読込不能lockを削除しない。force unlock / recovery APIはない。
- gateはnon-reentrant。`withCanonicalGate({root, operation, fn: async (gate) => ...})`内から内側APIへ同じ`gate`を明示する。暗黙のnested取得は`GATE_NESTED`、競合する取得は`GATE_BUSY`、破損は`GATE_CORRUPT`。leaseはrootとprocess内の実体にbindingし、release開始で再利用不可。callback完了前に作業をすべてawaitし、別作業とleaseを共有したままreleaseしない。
- [`fn004-repository.js`](../../src/fn004-repository.js) の `createFn004Repository(root)` / `readValidatedCanonicalSnapshot(root, {gate}?)` は同gate下でSlice 1のsnapshotを読み、validation失敗を`CANONICAL_INVALID`＋元diagnosticsとしてthrowする。snapshotはreadonlyの一時点のcopyで、release後も現在値との一致は保証しない。後続writeは再取得・manifest再検証が必要。
- `withCanonicalRead`はFN-001 / FN-003 / collectorにも適用するが、既存readerの返却形・部分検証は維持する。collectorのネットワーク取得・candidate保存やranking生成処理全体をgate内へ入れない。testsは実canonicalを一時directoryへcopyし、production stagingにlockを作らない。
- Slice 2時点のpresence guardは、Slice 3で[bootstrap runtime](FN-004-初期化・ID状態.md#slice-3-runtime-api)のtyped genesis/state検証へ置き換える。正常bootstrapは通常readerでも受理するが、未知request/transaction、非初期stateの未証明chain/pending、不完全bootstrap、cleanup未完了を普通のcanonical readで無視しない。実Apply journal/requestのschema・recovery実行は後続sliceの責務。
- [`persistence.js`](../../src/persistence.js) の `createPersistence(root)` はroot内POSIX pathだけを扱う低水準primitive。readJsonはobject rootのみで、missing / I/O / UTF-8 / JSON構文 / root型を別codeで区別し、domain schema/versionは判定しない。writeJsonAtomicは同directoryのUUID付きtempをwx作成→write→file sync→close→再読込一致確認→rename→directory sync。createJsonExclusiveは完成tempをhard linkでno-clobber公開→directory sync→自己temp unlink→directory syncする。
- 永続化失敗はphase・published・tempを伝え、公開後のdirectory sync/cleanup失敗も成功扱いしない。rename前の失敗で元fileを触らず、失敗tempは無差別削除しない。directory新設時はparentをsyncする。primitive自体はgateを取らず、repositoryのwrite/createはlive leaseを要求する。repositoryのJSON pathは正式staging artifactに限定し、canonical write APIを持たない。artifactごとのschema・immutable/mutable policyは後続domain layerが担う。
- traversal、絶対path、Windows drive/backslash、symlink ancestor/final pathを拒否する。Node標準APIによるpath検査とunlinkは非協調processの置換との競合を完全には防げない。local・同filesystem・協調operation前提を維持し、NFS/SMB/cloud同期filesystemへ保証を拡張しない。Linux/Node 20 CIで検証し、Windows等でdirectory sync/hard link/renameが成立しなければ明示失敗とし、弱いdurabilityへfallbackしない。
- Git管理方針は[全体設計](レビュー準備・canonical反映の全体フロー.md)を維持する。今回ignoreするのは導入したgateと`.fn004-*.tmp-*`のみ。Decision/Approval/History/bootstrap/stateをignoreしない。Plan/Request/journal/backupのignore追加は各runtime導入時に行う。

```text
staging/transactions/<transaction_id>/
├── transaction.json          最新journal recordの参照cache
├── journal/000001.json       sequence/hash連鎖の状態snapshot
├── intent.json              不変の実行前提・original/target・各identity
├── plan.json
├── decision-snapshot.json
├── approval.json
├── request.json              immutable receipt部分のcopy
├── backup/data/              全14 CSVのcopy snapshot
├── backup/fn004-state.json
├── temp/data/                changed CSVだけ
├── temp/apply-history.json
└── restore/                  backupを消費しない復元temp
```

transaction_idは`tx_<UUID v4>`、apply_idは同UUIDの`apply_`形式で1対1。receipt受付時に固定する。recoveryは同identity、新しい要求は新identity。

temp / backupはexclusive createし、書込 → file sync → close → 再読込/hash検査 → directory sync。予期しないexisting temp、別filesystem、欠落canonicalはSTOP。backupはhardlinkやrename退避でなく全14表のcopyで、元snapshotとのbyte hash一致を要求する。Gitだけを復元手段にしない。

journalはmutable recovery stateを追記型immutable recordsで表現する。各recordにsequence / previous_record_hash / record_hash、state、request/approval/Plan/Decision identity、original/target manifest、affected paths、temp/backup hash、per-file progress、ID state前後、History予定、時刻、error/recoveryを持つ。新recordをtempで完成・sync後にno-clobber公開しdirectory syncしてから次の副作用へ進む。latest cacheはtemp＋renameで更新する。

journal内容を読めない、未知version、hash連鎖破損はSTOP。latest cacheだけ失われ、全recordsとintentが検証可能なら参照を再構築できる。不正recordを無視して古いstateへ戻さない。progressはrenameより遅れるため、復旧の事実判定には実file hashを使う。

## state machine・commit

```text
PREPARING → PREPARED → COMMITTING → COMMIT_DECIDED → HISTORY_COMMITTED → COMPLETED
    |          |           |
    +----------+           +→ ROLLING_BACK → ROLLED_BACK
         ↓                              |
      ABORTED                           ↓
                                 RECOVERY_REQUIRED
```

| state | canonical | History |
| --- | --- | --- |
| PREPARING / PREPARED | original | なし |
| COMMITTING | original / 混在 / 全targetの可能性 | なし |
| COMMIT_DECIDED | 全target・検証済み | 未公開の場合あり |
| HISTORY_COMMITTED | 全target | 完全record |
| COMPLETED | 全target、state整合 | 完全record |
| ROLLING_BACK | original / target混在可能 | なし |
| ROLLED_BACK / ABORTED | original | なし |
| RECOVERY_REQUIRED | 実hashで判定 | 実在を検査 |

manifest / backupは全14表、commitはchanged filesだけ。順序はworks → creators → artists → releases → songs → song_artists → song_creators → song_performers → release_tracks。各rename前に期待hashを確認し、rename後にdestination directory sync・hash確認・progress追記を行う。順序だけでatomicとはみなさない。

COMMIT_DECIDEDはdurableな不可逆の成功方針であり、その後のHistory / state / journal失敗ではrollbackせず元transactionをfinalizeする。保存済みPlanの値を変更しない。外部の未知変更を検出したらforwardで上書きすることもせずSTOPする。

## rollback・recovery matrix

COMMIT_DECIDED前の部分commit・検証失敗は原則rollback。先にROLLING_BACKをdurable記録し、backup hashを検証、targetになったfileだけを逆順でrestore tempからrenameする。backupは保持し、originalになったfileは触らない。全14表whole validation＋original manifest完全一致後にROLLED_BACK。途中のknown-mixedとsemantic validationの扱いは後述の「Canonical byte provenance・known-mixed Recovery」を正とする。ID stateのpendingを解消するが消費上限は下げない。復元途中失敗はlock/artifactsを保持してRECOVERY_REQUIRED。

| crash / failure地点 | 判定・復旧 |
| --- | --- |
| Approval後・receipt前 | 実行未受付。承認だけでは自動dispatchしない。明示submit時に再検証 |
| receipt後・journal前 | 他要求を停止。owner終了、canonical/History/ID state・artifactsを照合し未開始を証明できればABORTED。判断不能ならSTOP |
| lock直後・journal初回前 | Planのoriginal前提と全stateを照合。根拠不足なら人間確認 |
| PREPARING / backup途中 / temp途中 | original一致・副作用なしを確認しABORTED |
| PREPARED | originalを確認してABORTED。自動でcommitを再開しない |
| COMMITTING、rename 0件 | original確認後ROLLED_BACK。消費IDは保持 |
| 一部commit、残りoriginal | backup一致・unknown hashなしならrollback |
| 全target、COMMIT_DECIDED前 | ROLLING_BACK方針がなく、保存した承認/入力根拠と実targetを再検証できれば成功確定してfinalize。不成立なら安全なrollback、unknownはSTOP |
| post-commit validation後・成功方針record前 | durable成功方針はまだない。直上と同じ再検証が必要 |
| COMMIT_DECIDED後・History前/書込途中 | 同recordを排他的公開してforward finalize |
| Historyあり・state/journal未完了 | History一致・target確認後、state成功headとjournalを完了 |
| COMPLETED後・lock削除前 | terminal整合とownerを確認してcleanup/unlock |
| ROLLING_BACK記録済み | targetが全件でもrollback方針を維持 |
| unknown hash / 欠落backup / 壊れたintent | 自動修復せず人間確認 |

自動recoveryはowner停止・recovery排他・信頼できる根拠がある場合だけ。no-opではoriginal==targetなのでbytesだけでなくstate/成功方針を使う。recoveryで現在のcanonicalへ合わせてPlanやapply_timeを再生成しない。

| filesystem error | 方針 |
| --- | --- |
| lock作成失敗 | EEXISTはBUSY、その他はwrite前STOP |
| receipt / 初回journal失敗 | canonical変更禁止。partial recordを無条件削除しない |
| backup / temp / temp validation失敗 | original確認してABORTED |
| ID消費state保存失敗 | canonical renameを開始しない。recoveryで消費有無確認 |
| canonical rename / sync失敗 | 実hash確認し成功確定前はrollbackへ |
| rollback rename失敗 | RECOVERY_REQUIRED、backup/lock保持 |
| commit後validation失敗 | 成功方針を記録せず、安全なrollbackまたはSTOP |
| History / 成功head保存失敗 | COMMIT_DECIDED以降はforward finalize |
| journal更新失敗 | 新副作用を止めlock保持。書けないRECOVERY_REQUIREDは戻り値でも通知 |
| journal finalization失敗 | 成功Historyを消さずfinalize待ち |
| lock削除失敗 | committedを取消さずcleanup_required |

permission denied、disk full、file locked、fsync失敗も同じ段階規則。通常process crash耐性を必須とし、sync未対応を黙って弱い保証へ切り替えない。

## successful Apply History

保存schema/hash/chain/set・readonly indexes・非初期state proofの正本は[History readonly契約](FN-004-成功履歴・読取検証.md)。従来のtrace部分だけの概念JSONを完全recordの代わりに使用しない。`staging/apply-history/<apply_id>.json`をGit管理し、成功1件につき1 immutable recordを完成tempからno-clobber・durable公開する。同ID同semantic hashは既存結果、異hashはintegrity STOP。

recordはpayload、record_hash、検証済みDecision/Plan snapshot、metadataを持つ。payloadの全内容をhashし、source Decision/Planは各semantic hash経由でbindingする。最終state_hashへの循環参照は作らず、before/consumed stateとallocation rangeを記録し、最終stateがrecord_hashを参照する。apply_time/applied_atは元COMMIT_DECIDED intentで固定し、retry/recoveryで変えない。published_at等の表示metadataだけはsemantic hash外。

成功HistoryはCOMMIT_DECIDED後に公開する。公開済みHistoryだけでjournal完了・owner停止・cleanup完了を断定しない。失敗・ABORTED・ROLLED_BACKは成功Historyに入れず、no-op成功も必ず記録する。History全体のchain/head/countと現在stateのproofを検証したうえで、通常reader/Planは既存runtime guardの未完了receipt/journal/pending/cleanup確認も必要とする。本人のrecoveryだけが保存intentを根拠に期待遷移を扱う。

History-only readonly proofはsuccess-only-v1 profileである。rollbackの消費済みID/eventを成功chainに偽装せず、追加のterminal journal proofが必要ならSTATE_TRANSITION_PROOF_REQUIREDで止める。後続Transaction/Recovery validatorがterminal整合を証明するまで通常利用を再開しない。この設計follow-upはpublication/recovery実装を含まない。

## ID state・bootstrap

bootstrap・genesis・initial stateの正式schema/hash契約は[Bootstrap / ID state](FN-004-初期化・ID状態.md)を正とする。Git auditは`origin/main` HEADから全parentを辿るreachable history、external declarationは全namespaceの人間監査upper boundとして必須。declared < current/history maxはblocking contradictionで、自動補正しない。

`staging/fn004-bootstrap.json`はGit-managedなimmutable genesis record兼completion marker、`staging/fn004-state.json`はGit-managedなmutable current state。repository_instance_idはstate lineageを識別し通常cloneで継承する。bootstrap identity payloadだけをJCS/SHA-256でhashし、audit/manifestをhash経由でbindingする。初期History headはbootstrap_hash、count=0、last_apply_id=null、allocation_events=[]、pending_transaction=null、generation=0。架空Apply/transaction recordを作らない。

bootstrapは明示check → 人間確認 → expected audit hash付きinitializeだけ。initializeでは監査を再検証し、stateを先にdurable/no-clobber公開、bootstrap markerを最後に公開する。片側file・残存bootstrap intent/temp・不一致は`BOOTSTRAP_INCOMPLETE`等で通常利用を止め、未初期化扱いや自動再bootstrapをしない。bootstrap専用intentは最小の中断証跡で、実Apply transaction journalやrecovery実行とは区別する。

stateのnamespace keyはcanonical ID prefix（W/C/P/G/L/V、song M/A/J/T/B/O/R/H）。全14個を保持し、0〜99999のinteger。99999はvalidな過去状態だが以後のallocationは枯渇STOP。Planは上限を読むだけ。COMMITTINGをdurable記録後、最初のCSV置換前にplanned IDsのrangeとtransactionをallocation eventとして消費し、high-water mark・generation・pendingを保存する。保存失敗ならCSVに触れない。

rollbackでも消費済み上限/イベントを残し、古いstate backup全体を戻さない。成功transactionは消費/pending確立でgenerationを+1、History公開後の成功head/count更新・pending解除でさらに+1とする（no-opも同じ）。他のjournal/receipt/cache更新ではstate generationを増やさない。History公開後に成功head/countを更新してpendingを解除する。no-opでも成功headは進む。state更新はtemp/sync/rename/directory sync。同transactionの消費を再度増やさず照合する。bootstrapの全namespace genesis、current/history max、直前valid stateより上限を下げない。初期化・clone・中断・schema validation・capacity・TOCTOUの詳細は上記専用契約に従う。

## 成功・cleanup・Git

成功はtarget全14表一致・whole validation・ID state整合・成功History一致・COMPLETED journalが揃った時点。requestのresult参照を同結果へ結び付ける。lock削除失敗は成功を取消さず、readiness=cleanup_required。COMMIT_DECIDED後未完了はcommitted_pending_finalization、再Applyは禁止。

未完了journal / receipt / backupはGCしない。terminal確認後だけtempを削除し、journal/backupは保管policyで後日削除可能。cleanup失敗で成功Historyを消さない。復旧に必要なPlanやreceiptは依存がある限り保持する。

Git commit / push / PR、site buildはtransaction外。Git失敗でcanonicalをrollbackしない。Apply後に人間がcanonical・Decision・Approval・History・stateのdiffを確認して通常のGitフローへ進む。直接編集との競合は直前/直後hashで検出するが、非協調writerとのcheck/rename間raceは防げないため、transaction中の直接編集・checkoutは禁止する。

### Intent lifecycle・pre-Intent abort（6A-DG01-01訂正）

Intentの有無はphase名や最新intent_hashだけでは決めない。単一transactionのOwner、全journal prefix、固定pathのIntentとpublisher temp、既存terminal proof/completionを共に検証する。以下はderivedな検証状態であり、保存field・phase enum・新しいartifactを追加しない。

- **未作成を検証済み**：正規intent.jsonがなく、Intent publicationの未解決temp/partialもなく、全prefixにnon-null intent_hashがなく、他の証跡にもIntent確立の参照がない。Owner/Binding、既知path全件、元canonical/state/History、未消費を検証できることが必要。file不在だけではこの状態としない。Intent未作成でもPREPARING中の完成済みbackup/temp subsetや計算済みtarget情報はあり得る。
- **確立済みH**：正規pathに単一の完全なIntentArtifactがあり、schema/hash/Owner/Binding/apply_time/original/target/before/expected-consumed、全input/backup/temp refsのprepare契約を満たし、durable publicationが確立した状態。Hはそのartifact.hash。後続phaseで許されるtemp rename/terminal cleanup後のphysical不在は既存規則に従い、Intent自体はv1で削除しない。
- **未解決または矛盾**：publisher tempだけ、partial/corrupt/unsupported、異内容の複数Intent、既知Hの原本欠損等。未作成へfallbackせずmanual STOP。path/I/O/parse失敗の元typed errorを保持する。

**公開順序とbinding境界**は次に固定する。

1. 初回PREPARINGをintent_hash=nullでdurable公開する。固定apply_timeでtarget・全backup/temp/inputをprepareする。Intentがないことを埋めるdummy hashは作らない。
2. 完全Intentを正規tempからno-clobber公開しfile/directory sync・readbackする。これが未作成→確立済みHの境界であり、journalへの参照追記より先。以後同一Intent全内容を維持する。
3. 次にjournalへHとそのtarget/changed_paths/全refsをbindingする。通常prepareではPREPARING(H)の確認checkpointを置いてもよく、直接PREPARED(H)へ進んでもよい。PREPARED以降へnullを持ち込まない。過去のtarget/refsが既にあれば変更せず、完成済みsubsetを同Intentの全refsへ拡張するだけ。

2と3の間のcrashは、**確立済みIntent H＋まだnullのnonterminal prefix**という合法なpublication lagである。最後のphaseがPREPARING、またはRECOVERY_REQUIRED(resume_phase=PREPARING)の場合だけこのlagを認める。journalにまだHがなくても、このTransactionを未作成と分類しない。新しく追記するentryは確認したHを必ずbindingし、nullで新checkpoint/terminalを作らない。

Recoveryは元owner終了・同common gate・全元入力/actual original/before state/History・全Intent/refsを再検証し、未消費・canonical置換なし・他unfinished workなしを証明できる場合だけ、既存Intentを利用してABORTED(H)へ進む。再prepare、Intentの新規公開/差替え、現在入力からの再生成、commit再開はしない。正規Intent pathに完全なIntent bytesが存在するが以前のdirectory sync完了を判断できない場合、所有権下で同じ既存bytes/必要directoryのsyncとreadbackを確認してからHを参照する。不完全なbytes/欠落refsをsyncで正当化しない。この確認ができなければSTOP。

RECOVERY_REQUIREDからは既存phase契約どおりresume_phaseへ確認entryを追記してからterminalへ進む。resume=PREPARINGなら、未作成検証済みはPREPARING(null)→ABORTED(null)、確立済みはPREPARING(H)→ABORTED(H)。これは方針確認でありprepareの副作用再開ではない。PREPARINGからの直接ABORTED(H)でbinding lagを解消する既存経路も維持する。

**chain不変条件**：null→nullは未作成検証済みの許可phaseだけ。null→Hは上記完全Intentの確認後だけ。最初にjournalへHをbindingした後は全後続entryで同じHを保持し、H→null、H1→H2を拒否する。journalが未bindingでも正規Intentが確認できれば確立済みとして扱う。過去null prefixをHへ書き換えず、追記で確認する。ABORTED(null)後のIntent作成/binding/PREPARING再開は禁止。terminal/proof/completionを後からIntentありの結果へ改変しない。

| journal phase | intent_hash=null | HとIntentの条件 / predecessor |
| --- | --- | --- |
| PREPARING | 初回・未作成checkpointで可。正規Hが先行するpublication lagの旧null prefixだけは許す | 確立済みHを確認した新entryはH。初回PREPARING自体は既存どおりnull |
| PREPARED | 不可 | 完全Intent/全refsと同H。PREPARINGからだけ |
| COMMITTING | 不可 | PREPAREDから同H、以後同phaseでも固定 |
| COMMIT_DECIDED / HISTORY_COMMITTED / COMPLETED | 不可 | 既存の成功phase遷移と同H。新しい成功境界は作らない |
| ROLLING_BACK / ROLLED_BACK | 不可 | COMMITTINGを経由した同H。未消費rollbackでもIntentは必須 |
| ABORTED | 全prefixにHなし＋未作成検証済み＋PREPARINGからのabort条件成立時だけ可 | 確立済みなら必ずH。PREPAREDからはH必須。公開済みIntentとABORTED(null)の共存は禁止 |
| RECOVERY_REQUIRED | resume=PREPARINGで、元prefixがnullの未作成状態または上記publication lagに限る | 元prefixにHがあれば同H必須。他のresume phaseはH必須。error entryはIntent有無の証明を代替しない |

この表はphase transitionを増やさない。nullのABORTEDは、journalなしreceipt-onlyではなく、PREPARINGを含む**journal-based pre-Intent abort**である。元canonical/state全内容を保持し、ID消費/pending/generation/成功Historyを変更しない。Intentがなかったことを理由に以前記録したtarget_manifest/changed_paths/完成refs subsetを消してはならず、ABORTEDはその既知情報を保持する。

TerminalProofはこの場合intent=null、journalはPREPARINGからABORTED(null)までの完全chain、phase=ABORTED、consumed_state=null、after_state=before_state、final_manifest=original、history=nullとする。journal=[]へ置換してreceipt-onlyに偽装しない。H確立済みならproof.intentはexact Intent、terminal entryもH。Completionは元proofへの既存exact bindingを使い、**journal-based pre-Intent abortのterminal_journalはABORTED entryの非null参照**、result=null。Intent不在はこの検証済みnull経路だけで合法。Proof以後の再abort禁止、元proof/time/authority再利用、Completion以後のcleanup/不要というM-01契約はそのまま適用する。

**fail-closed**：H→null、H1→H2、non-null HとIntent欠損/異hash、正規Intentとterminal null、null terminalなのに以前のH参照、複数/未知path/異内容/不正schemaのIntent、proofとIntent状態の不一致、Completionとproof不一致、成功/消費証跡とpre-Intent ABORTEDの共存を拒否する。terminal以後にIntentが見つかっても後付けで結果を修正しない。元INTEGRITY_CONFLICT、STATE_TRANSITION_PROOF_REQUIRED、PERSISTENCE_*等のtaxonomyと既存readiness優先順を使う。未解決publication/証明不足はreadiness=recovery_required、diagnostic=RECOVERY_REQUIREDとactionなし。新action/readiness/codeを追加しない。

Intent確立の有無は、同一abort action内の合法なterminal evidenceを決める条件であり、新actionではない。M-01のterminal evidence優先を先に適用するので、公開proof/Completionがあればabortへ戻らない。H-01の永久archive・claim/sequence・Retiring/Retired・barrier順序は不変で、pre-Intent終端にも同じretirementを適用する。COMMIT_DECIDED以後、ID消費後、ROLLED_BACK/COMPLETEDへnull許可を拡張しない。

LOCKEDはjournal enumに含めない。terminal後のowner移管/cleanupはMutexProofとcompletion/proof検証で扱い、terminal entryを書き換えない。同phase checkpointは既知情報を消さず、progressを戻さず、固定値を変更しない。RECOVERY_REQUIREDでもchain中のCOMMIT_DECIDEDまたはROLLING_BACKは失われない。success decisionを一度でも記録したchainからrollback/ABORTEDへ遷移できない。ROLLING_BACKを記録したchainからsuccessへ転換できない。

実stateがconsumedだがcheckpointがまだid_consumed=falseの場合、Recoveryは同COMMITTINGの確認checkpointを先に公開しtrueへ進める。逆に消費済み証跡があるのに実state=beforeなら巻戻し矛盾としてSTOPする。

COMMITTINGで全target・id消費済み・ROLLING_BACKなしの場合だけ、元Approval/入力/Plan/real target/History prefixを再検証してCOMMIT_DECIDEDを確定できる既存例外を維持する。失敗なら検証済みbackupでrollback、unknownならSTOP。no-opはoriginal==targetなのでbytesだけでは例外を適用せず、durable COMMITTINGと実consumed stateが必要。

COMMIT_DECIDED entryのhistory.recordをその前にメモリで完全構築・既存validator/hash/prefixで検証する。applied_atはこのentry.recorded_at、metadata.published_atもこの最初のpublication intentの同時刻に固定。apply_time <= applied_atを要求する。entryのdurability成功前にはHistoryを公開しない。Recoveryはentry内の元record全体を再利用し、metadataも再生成しない。decision前のtemp Historyは成功根拠ではなく、採用しなければ公開しない。

### Terminal proof・completion・state合成（DG-04）

TerminalProofPayloadの全field：

| field | 型・条件 |
| --- | --- |
| binding / owner | Binding / OwnerArtifact |
| inputs | {decision:Revision, plan:ApplyPlan, approval:ApprovalArtifact, request:ReceiptCopy} |
| intent | IntentArtifact\|null |
| journal | JournalEntry[]、sequence順。receipt-only ABORTEDだけ[] |
| phase | "ABORTED" / "ROLLED_BACK" / "COMPLETED" |
| before_state / consumed_state / after_state | Fn004State / Fn004State\|null / Fn004State |
| final_manifest | 全14 Manifest。失敗はoriginal、成功はtarget |
| history | HistoryRecord\|null。COMPLETEDだけ元decision recordと完全一致 |
| authority | terminal確認者のAuthority |
| ended_at / diagnostics | Timestamp / [{code:ExistingCode}]。journalありは最後のterminal entry.recorded_at、なしはABORTED証明時に固定。diagnosticsはcode ASCII順unique |

CompletionPayload={binding:Binding, phase:"ABORTED"|"ROLLED_BACK"|"COMPLETED", proof_hash:Hash, terminal_journal:JournalRef|null, ended_at:Timestamp, diagnostics:[{code:ExistingCode}], result:{apply_id:ApplyID,record_hash:Hash}|null}。diagnosticsはcode ASCII順unique。terminal_journalはproofの末尾entry、空journalの場合だけnull。resultはCOMPLETEDのverified History参照だけ。失敗は必ずnull。proof hash・identity・phase・ended_atとexact一致。completion単独/processing文字列だけでterminal認定しない。

terminal entry→terminal proof→completionを順にdurable公開してからcleanup/unlockする。receipt-onlyはowner＋input snapshotsからproof→completion。completionはRequestごとに一つ、元終了時刻と全内容を保持。同identity別proof/結果はconflict。completionのdiagnosticsもproofと完全一致。proof.authorityはjournalありでは末尾terminal entry.authority、なしでは元Ownerまたは検証済みRecovery authorityに固定する。途中crashでproof/completionがない場合、既存terminal証拠を再検証して同じended_at/内容を完成する（新terminal stateを生成しない）。journalなしのended_at/authority/diagnosticsは最初のproof publication intentで固定する。完成・sync済みpublisher tempが残れば全schema/元証拠との一致を検証して同じ内容を公開し、時刻を再生成しない。partial/unreadable tempはSTOP。新proofを生成できるのは既存完成intentも公開proofもないと証明できる場合だけ。

proof内inputsはOwner/Bindingの元Decision/Plan/Approval/ReceiptCopyと全内容/semantic hash一致。intent_hashがchainにあれば同hashのintentが必須で、なければintent=null。ただしnullを許すのはIntent lifecycle表で未作成を検証したreceipt-onlyまたはjournal-based pre-Intent ABORTEDだけで、正規Intentの存在/既知Hを無視しない。consumed_stateは実消費確認の有無と一致し、after/final_manifest/history/authorityは末尾terminal entryまたはreceipt-only ABORTED証明と一致させる。

Terminal proofは新しい成功Historyではなく、失敗を含むstate遷移の検証材料。inputs全schema/semantic hash、全Binding、Owner、intent、journal chain/phase・authority、全state hash/lineageを再検証し、埋込snapshotを自己申告boolで代用しない。COMPLETEDは外部successful History原本とも全内容一致。失敗は対応する成功Historyが全件検証済み集合に存在しないことを要求する。raw backupをproofへ埋め込まず、final_manifestとterminal時のwhole validationはtrusted writerが実bytesで証明する責務。通常readonlyが過去canonical bytesを現在値として再生したと主張しない。

state遷移は次に固定する。全例でstate_hashを既存hashStateで再計算し、記載外fieldは全内容不変。

| 場合 | before→consumed→after |
| --- | --- |
| 消費前ABORTED | consumed=null、after=before。stateを書かずgeneration増加なし |
| COMMITTINGだが実消費なしのROLLED_BACK | consumed=null、after=before。canonical置換/progressなし、original検証必須 |
| 消費後ROLLED_BACK | consumedはHistory契約と同じgeneration+1／pending=tx／ranges append／high-water増加。afterはconsumedからgeneration+1、pending=nullだけ変更。History head/count/lastはbeforeのまま |
| COMPLETED（no-opを含む） | 同じconsumed。afterはさらにgeneration+1、pending=null、historyを当該successful recordのcount/hash/applyへ更新 |

journalのconsumed_state期待値と、proofのconsumed_state（実消費確認済み）を区別する。実stateがbeforeでもexpected consumedでもない場合に状態を推測しない。消費後rollbackはallocation_eventsもhigh-waterも保持。Recovery再送はbefore/consumed/afterの全document/hashで比較し、同遷移を二度加算しない。ABORTEDを消費済みfailureへ使わない。

追加の内部proof profile名はtransaction-terminal-v1。既存success-only-v1 API/DTO/判定は変更しない。合成validatorは次の順で検証する：

1. genesis再構成、全Historyの既存schema/hash/chain/set/index/Plan-prefix検証を共用する。success-onlyのstate proof失敗だけを成功へ書き換える実装は禁止。
2. 全terminal proofをstrict検証し、tx/request/apply identityは各一意。COMPLETED proofとHistoryは同recordへ対応し、二重state edgeには数えない。従来の成功Historyだけでもその既存before/consumed/afterを一つのsuccess edgeとして使える。
3. state-changing edgeをbefore.generation数値順に接続する。各beforeが直前afterとJCS全内容一致、after.generation=before+2。同じbeforeから別edge、gap、未参照edge、range重複/欠損を拒否する。失敗edgeは成功History sequenceを進めない。
4. zero-change ABORTED/未消費ROLLED_BACKは、導出済みcheckpointの同before/afterに一致する場合だけ検証し、generation edgeを追加しない。当該Planのstate/history preconditionもそのcheckpointへbindingする。
5. 最後のafterとcurrent state全内容一致、pending=null、全14 canonical whole validation、genesis/current/Git全履歴以上のhigh-waterを要求する。成功History setとstate.historyも一致。
6. 各local Request/journal/completionをproofにexact対応させ、未完了/unknown/壊れたentryを残したまま通常利用可にしない。既存Approval/Invalidationのglobal validationを省略しない。

通常Plan/lookupの新しい内部contextは同leaseでservice自身がcomposite proofとvalidated History indexesを取得した場合だけ作る。既存lookupVerifiedHistoryへsuccess-onlyのfalseをtrueに書換えて渡さず、composite検証済み内部contextから既存pure lookup logicを再利用する。caller提供のproof flagは不可。readApplyHistory/verifySuccessfulHistoryの旧profile/DTOとready-only helperの失敗境界は維持し、追加contextを旧結果へ偽装しない。

この合成profileは6C/D/Eで接続する。6Aはschema/pure proof検証までで通常readerを解除しない。過去terminalのfinal_manifestと現在canonicalの不一致だけで過去成功を取消さない既存History契約も維持する。一方、未完了transactionのunknown canonicalは必ずSTOP。

Git-managed stateの消費履歴をclone後も証明するため、terminal proofは独立したGit-managed pathに保持する。Git非管理journal/completionの有無を成功Historyへ混ぜない。state/Historyをcommitする運用では対応proofも同じdiffで確認するが、Git操作自体はTransaction外。cloneでlocal Receiptがないときに再発行・再dispatchはしない。History readonlyのReceipt非依存境界は維持し、Invalidationの元Receipt必須検証も緩めない。

v1はterminal proof・元Owner/input/intent/journal/completionを削除/GCしない。全terminal証明公開後だけ、列挙済みbackup/temp/restoreと既知publisher tempを検証してcleanup可能。未知pathをsweepしない。proofはlocal証跡を保持する限りそれらと一致必須。Git cloneでlocal runtime directoryがないことは、完全なproof packageとHistory/stateから検証できる場合だけ許す。不完全packageはSTATE_TRANSITION_PROOF_REQUIREDまたはintegrity errorで止める。

| runtime観測 | readiness / 通常利用 |
| --- | --- |
| 全terminal proof/state/History一致、pendingなし、cleanup不要、gate正常 | initialized。失敗terminalでも同じ |
| terminal proofとcompletionまでvalid、既知temp/backup/lock後片付けだけ残る | cleanup_required。通常利用は止める |
| 未完了、proof/completion不足、観測競合、未証明state、owner不明 | recovery_required |
| canonical validation、lineage/schema/integrity等の既存blocking不正 | blocked。後述のVerified Known-Mixedを証明したRecovery内部の一時的semantic FAILだけはrecovery_required。typed errorを通常DTOへ隠さない |

複数条件のreadiness優先順は、後述のVerified Known-Mixedの閉じたRecovery例外を除き、canonical/lineage/domain schema/hash/History不正のblocked、未完了/proof不足/owner不明/raced/非terminal activeのrecovery_required、検証済みterminalの既知cleanup/retirement/barrier解放だけのcleanup_required、全条件正常のinitialized。terminalがvalidでownerがliveの場合もcleanup_requiredと外部actionなしを両立する。gate破損は通常操作ではthrowを保持し、inspectで診断できる場合はrecovery_requiredとactionなしを返す。domain不正とgate破損が同時ならblockedを優先する。

readinessはrepository軸、phase/outcomeは要求軸。result非nullとrecovery_required/cleanup_requiredは共存する。Request DTOのfield/enumを追加しない。非成功terminalはresult=null、検証済みcompletion/proofを専用status/Recovery inspectで観測する。processing原本を表示用truthへ更新しない。

### 正当なpublication lagとintegrity conflict

checkpointは実際の副作用より遅れ得る。次のactual state/Historyだけを本人の検証済みintent/chainから期待遷移として認める。通常readerやcallerのpending bypassに使わない。

| 最後の方針 | 許可するactual state / 当該History |
| --- | --- |
| PREPARING / PREPARED | before / なし |
| COMMITTING | beforeまたはexpected consumed / なし。state消費のreadback checkpoint遅延を含む |
| ROLLING_BACK | before、consumed、または厳密に導出したfailure after / なし。afterならpending解除を再加算せず、original/whole validation後にROLLED_BACKを完成 |
| COMMIT_DECIDED | consumed / 元prefix、または元prefix＋entry内のexact成功recordだけ |
| HISTORY_COMMITTED | consumedまたは厳密に導出したsuccess after / 元prefix＋同record |
| terminal | そのproofが要求するafter / 成功なら同record、失敗なら元prefixだけ |

RECOVERY_REQUIREDはresume_phaseにこの表を適用する。別txのpending、異History、余分なrecord、未知のstate hash、表にない先行更新を「遅延」として救済しない。History prefixのcount/head/last/semantic hashと全recordの既存検証は必須。

success-only-v1がstate.historyの一時的lagを理由にvalid=falseを返す場合、そのfalseをtrueへ変換しない。追加の内部transaction-terminal-v1 observationは、全Historyの既存schema/hash/chain/set/Plan-prefixと、当該COMMIT_DECIDED根拠・exact record・上表のconsumed stateを同leaseで検証して、当該Requestの成功参照だけを証明できる。通常readinessはrecovery_requiredで、Plan/新Request受付には使えない。この場合もHash/参照/History構造破損をresult=nullや通常diagnosticへ丸めない。full terminal state proofと、限定された成功観測を区別する。

### Canonical byte provenance・known-mixed Recovery（6C-DG05-01訂正）

<a id="known-mixed-recovery-contract"></a>

**目的・適用範囲**：通常canonicalのsemantic validityと、当該Transactionのbyte provenanceを別軸で検証する。multi-file置換/逆順restoreでは、各fileが正しいoriginal/targetでも全表のFK・required relation等が一時的に成立しない。これは本節の全証明を満たす場合だけRecovery上の既知途中状態であり、一般のcanonical corruptionではない。canonical validator、通常readerのwhole-valid要件、終端前のwhole validationを弱めない。以下はderivedな検証結果で、保存field/schema/hash/version、readiness/action enumを追加しない。

#### 1. Endpointsとfile単位の分類

Oは元Owner/Planへbindingした全14 original、Tは同じBindingの単一Intentへbindingした全14 target、Cは実canonical全14の同一観測bytesとする。単にmanifestがあるだけではendpointをvalidatedとしない。以下1〜4の完全prepare証明はKnown-Mixed/rollbackのための条件であり、receipt-only/PREPARINGの既存abortへ未作成Intent/T/未完成backup/input copiesを要求するものではない。

1. Owner/Receipt/Plan/Decision/Approval、repository instance/bootstrap、全journal prefix/hash/phase/authority、Intentのschema/hash/同一H/apply_time、全input copiesとsource原本、全backup refs（14 CSV＋before state）、required temp/restore refs・publisher tempを既存規則で検証する。別tx/repository、fork/gap、partial、unsupported、必須欠損、success/failed矛盾、他unfinished workは例外対象外。ProcessingCache/latestは根拠にしない。
2. Oの14 raw bytesは検証済みbackup copyから取得し、Owner.original_manifestとPlan.canonical_preconditionへexact binding、全表whole validationを要求する。backup/stateもOwner.before全内容と照合する。current mixedをOとして採用したりPlanからOを逆算しない。既存の未消費abortでは、Cの全14同bytes snapshotがOwner/Plan.original manifestに完全一致しwhole validなら、これをAll-Originalの証明に使える。Tが未作成でもこの経路は合法で、Tを捏造しない。
3. Tは保存済みPlan execution payloadとO、初回PREPARINGの固定apply_time、serializer=1から決まる。全14 Tのwhole validation、元row不変/許可insert、実raw manifest=Intent.target_manifest、changed_paths/全refs一致を検証する。物理T bytesが揃う場合はそれらも同じ実targetと照合する。rename/restore済みでTの一部が失われたときは、この**元O・元Plan・元時刻だけ**によるメモリ内replayをTの検証に使ってよい。新Intent/ID/time/backup/tempを作成せず、physical presence不足を補った扱いにしない。replayはI/O/readback失敗や不在判定不能を合法なrename済み欠損へ変換しない。元inputs/serializer/rulesを検証できない場合はSTOP。
4. Cは全14 regular fileを安全path・strict UTF-8/CSV/header/列/field/ID規則で読み、同bytesから長さ/hash/manifest/rowsとfull domain validation結果を取得する。read/path/parse失敗は元typed errorを保持し、仮の空bytes/nullをoriginalへ変換しない。CとO/Tの比較はpath、byte_length、SHA-256と実bytes一致で行い、semantic normalizationは使わない。同length/hashなのに比較可能なbytesが異なればintegrity conflict。OとTの該当file同hash/長さ・異bytesも拒否する。

fileのmembershipを`O(p)=C[p]とO[p]がexact一致`、`T(p)=C[p]とT[p]がexact一致`と定める。ORIGINALはO(p)、TARGETはT(p)、UNKNOWNは両方不成立または必要根拠が検証不能。非変更fileでは両membershipがtrueになる。これは二つのpredicateであり、勝手なprecedenceで片方へ丸めない。O/Tのraw manifest差分だけを既存順に並べたD=changed_pathsを使う。

| aggregate | exact条件 |
| --- | --- |
| All-Original | 全14でO(p)。D上のTARGET-onlyは0 |
| All-Target | 全14でT(p)。D上のORIGINAL-onlyは0 |
| Known byte mixture | UNKNOWN=0、D上にORIGINAL-onlyとTARGET-onlyが各1件以上 |
| Verified Known-Mixed | Known byte mixtureに加え、本節のendpoint/全evidence、phase/state/trace、success/terminal排除、gate構造の全条件を満たす |

D=[]のno-opはAll-OriginalかつAll-TargetでありKnown-Mixedではない。D非空なら上三aggregateは排他的。非変更5表や、その他unchanged fileの両membershipをmixedの件数へ足さない。byte membership自体はfile順・phase・listing順と独立だが、**Verified**認定とactionには次のtransition証明が必要である。

#### 2. Phase/state/進行証明（任意の組合せを許可しない）

common gate、全ownership archive/head/barrier/retirementの構造とphysical witnessをDG-03どおり検証する。非terminal semantic workにACTIVEの正しいauthorityが必要で、RETIRING/RETIRED/SEALEDから再実行しない。外部inspectのowner終了/OS proof条件とrunの再取得・再観測は別の必須guardであり、本節で緩めない。

- PREPARING/PREPARED・receipt-onlyは既存どおりAll-Original＋actual before＋未消費だけ。Known-Mixedをpre-Intent/abortへ流用しない。Intentなし/不正/不明を既知targetと扱わない。
- COMMITTINGのKnown-Mixedはactual stateが**exact Intent.expected_consumed_state**であることを要求する。id_consumed=falseのlagは既存どおり同COMMITTINGの確認checkpointを先にdurable化する。actual before＋TARGET-only、またはid_consumed=true＋actual beforeは矛盾でSTOP。state消費・新allocationをRecoveryで実行して補わない。
- 正規commit順Dに対し、COMMITTINGのactual TARGET-only集合はDのprefixで、記録済みreplaced_pathsはそのprefix内の先行prefix。記録が実renameより遅れることは許すが、記録済みreplacementがoriginalへ戻っている、または順序と両立しない組合せはUNVERIFIED/INTEGRITY_CONFLICT。
- 保存済みinputs/endpointの再検証に加え、current input_revalidationはvalidまたはstaleとして判定可能であることを要求する。staleはKnown-Mixedのrollbackを妨げないが、unavailableをstale/validへ推測しない。必須根拠のmissing/I/O/不正は元typed error/diagnosticで停止し、評価不足だけならmanual_stop/[]・RECOVERY_REQUIRED。C semantic FAILで本例外を証明できない場合は通常のblocked優先を適用する。
- ROLLING_BACKへ移る前に、所有権下でactual consumptionと**実replacement prefix全体**を確認し、未記録なら同COMMITTINGの確認checkpointへ追記する。既存id_consumed/target/H/ref/progress単調性を守り、normal commitや新renameを再開する意味ではない。これで最初のROLLING_BACKのreplaced_pathsをPとして固定し、restore開始前にPとrollback方針をdurable化する。PはDのprefixであり、その時点の実target全件と一致する。
- ROLLING_BACKでは新replacementを増やさない。actual TARGET-only集合UはPから既存逆順restoreで除いた残りで、`P\U`はPの逆順prefixに相当する。記録済みrestored_pathsは、このactual restore集合に含まれる逆順subsequenceで、過去checkpointから縮めない（実restoreへのlagや未checkpointの完了を許す）。P外にTARGET-onlyがある、記録済みrestoreがtargetへ戻る、逆順実行と両立しない組合せはSTOP。
- ROLLING_BACKのKnown-Mixedでもactual consumedが必須で、COMMITTING中のid_consumed=true確認prefixを要求する。ROLLING_BACKでfalseのままactual consumed/failure-afterなら、COMMITTINGへ戻して補わず矛盾としてSTOPする。actual beforeは未消費・canonical/progressとも置換なしのAll-Originalだけ、failure-afterは全14 All-Original/whole valid後だけに限定する。R77-H01のstate先行/巻戻し矛盾をbytesの一致だけで救済しない。
- 既にROLLING_BACKなのに不足したPを現在値からCOMMITTINGへ戻って補完したり、terminal journalへ追記し直したりしない。Intent物理ref欠損の例外は既存のrename/restored証明に限定する。復元済みoriginal＋target temp欠損には過去のreplacement/restore参照が必要で、未証明欠損をreplayで隠さない。

このtraceはcommit方向だけを認定する規則ではない。ROLLING_BACKの部分restore後も別のKnown-Mixedとして同じ判定を繰り返し、cross-table validationが一時的にFAILしていても継続を証明できる。一方で任意のO/T組合せを正規状態とは認定しない。既存のforward/逆順restore順序、同phase checkpoint、既存progress fieldだけを使い、新しいstate/actionは不要。

#### 3. ID high-waterとvalidationの使い分け

C全表validation FAILを理由にstate/Git監査を省略しない。actual stateの完全schema/hash/lineage/events、元before checkpoint、expected-consumedの厳密なgeneration/pending/range/event遷移を検証する。Known-Mixedではactual=consumed、namespaceごとのhigh-waterは、**whole-validated OのID maxima、whole-validated TのID maxima、bootstrap genesis、完全origin/main historical maximaの最大以上**を必須とする。各C fileがO/T exact bytesなので、このboundはactual current使用IDもcoverする。invalid mixedをwhole-validと偽装して既存currentIdMaxima/success-only APIへ渡さず、検証済み両endpointの既存ID audit結果を内部contextで使う。audit不可・不足は元error/STATE_HIGH_WATER_INVALID等でSTOP。

これは既存lower boundの実装可能な証明方法で、IDを新規消費する規則ではない。rollback後もhigh-water/allocation_eventsを保持し、pending解除と既存failure generation遷移だけを一度行う。before/consumed/afterの全document一致でreplayを判定し、二重incrementしない。All-Originalの未消費caseへT maximaを強制して新ID消費を要求することもない。

semantic validationは省略しない。O/Tは常にwhole valid、Cも常にfull validatorを実行し結果を保持する。**Verified Known-Mixed＋pre-decisionのrollback-safe条件がすべて成立する場合だけ**、CのFAILを通常のcorruption/UNKNOWNへ昇格させず、rollback限定の一時的不整合として扱う。validator codeによるallowlist、message分岐、正常process内だけの特例は禁止。同じerrorでもunknown bytes/根拠不足ならこの例外は成立しない。All-Original/All-Targetでfull validationがFAILすればendpoint/bytes/rulesの矛盾であり例外にしない。

#### 4. Priority・readiness・diagnostics・action（exact mapping）

まず全artifact/lineage/hash/physical evidenceを検証し、M-01どおりCompletion→Proof/完成proof intent/terminal journal→COMMIT_DECIDED/当該successful Historyの段階を確定する。**Known-Mixedのrollback例外は、そのどれもないCOMMITTING/ROLLING_BACKでだけ**評価する。phase=RECOVERY_REQUIREDは保存resume_phaseと過去policyへ同じ条件を適用し、既存規則どおりresume確認後にだけ副作用へ進む。未完了terminalization/cleanup中はactual final canonical/stateのexact一致を要求する。完全に片付いた/SEALEDな過去terminalの後に正当な別transactionや編集がある場合は、既存historical/composite検証境界を保ち、旧O/Tとのcurrent不一致だけで過去proofを矛盾扱いしない。過去terminalをrollback対象として再開することもない。

#### 5. Rollback再分類・crash regression

各checkpoint/rename前後、owner継承、throw/SIGKILL/power-loss equivalent後の再開で、同じO/T/C・state・trace・terminal/success priorityを再検証する。前回のvalidation結果、PID、mtime、cache、process memoryだけを継続根拠にしない。UのTARGET-only fileだけをDの逆順に、verified backupの原bytesからrestoreする。既にOのfileは触らず、backupは保持する。各restore中はC full validationがFAILしてもCase Cなら継続可。全14 Oへ戻った後はC whole validationとoriginal raw manifest完全一致を**必ず**要求してからfailure-after/pending解除・ROLLED_BACK・Proof・Completionへ進む。途中をROLLED_BACK/terminal proofで覆わない。

| crash point | byte/semantic状態 | readiness / diagnostics / candidate action |
| --- | --- | --- |
| first replacement前 | All-Original、PASS、COMMITTING | Aのrollback。actual before/consumedを区別。recovery_required / RECOVERY_REQUIRED |
| first replacement後 | Known-Mixed（Dが1件だけならAll-Target）、PASSまたはFAIL | B/Cならrollback。All-TargetならDの厳密な分岐。Cは元validation codesも残す |
| middle replacement | traceに適合するKnown-Mixed、PASS/FAIL | B/C rollback、recovery_required。unknown/nonprefix/state矛盾はE/FでSTOP |
| last replacement後 | All-Target、PASSが必須 | Dのsuccess例外/stale rollback/STOP。COMMIT_DECIDED以後をrollbackしない |
| first restore前 | ROLLING_BACK＋fixed P、All-Original/All-Target/Known-Mixed | 方針どおりrollback。P/H/consumptionの確認checkpoint不足はSTOP |
| first restore後 | Uが逆順で縮小したKnown-Mixed、PASS/FAIL | B/Cのrollback継続。progress lagをactual bytesとPで証明 |
| middle restore | 同じrollback traceの別Known-Mixed、PASS/FAIL | B/Cの同一predicateを再評価。state/権限/証跡変化はSTOP |
| last restore後・rollback validation前 | All-Original。full validation未確認なら終端不可 | rollback/recovery_required/RECOVERY_REQUIREDのまま実whole validationを行う。FAILならblocked/[]、成功推測なし |
| rollback validation後・ROLLED_BACK前 | All-Original・PASS・exact manifest、許可state | rollback kernelが同じfailure遷移/terminal journalを一度完成。generationを再加算しない |
| ROLLED_BACK後・Proof/Completion前後 | All-Original・PASS、exact terminal証拠 | M-01のfinish_terminal→cleanup/不要。rollbackへ戻らない |

代表例（6C-DG05-01）：新songとprimary song_artistを含むvalid targetで、songsまでtarget・song_artistsはoriginalのCOMMITTINGはPRIMARY_ARTIST_MISSINGでもCase C。song_artistsまでtargetならCase B。同状態からROLLING_BACKでsong_artistsを先にoriginalへ戻した直後もCase Cであり、songsのrestoreへ継続できる。各file exact O/T、actual consumed、全backup/入力/Intent/trace・ownership等が条件で、同じerror名のunknown corruptionはE/FでSTOP。この例は順序変更では解決せず、relation先行ならFK不整合が生じ得る。

#### 6. Compatibility・実装handoff

Pre-Intent null→H単調性、H-01永久archive/sequence/OS証明、M-01 terminal priority、R77-H01 state/canonical順序、R77-H02 gate binding、R77-M01 Intent非依存input-copy照合、R78-M01 process crash境界、R78-M02 typed I/O evidenceを維持する。Intent欠損/破損でVKMを判定する代替fallbackはない。receipt-only/pre-Intent abort自体は従来どおりAll-Originalで完結する。

Observation v2はO/Tの根拠となるOwner/Intent/全refs/inputs、current raw files、全journal/authority/retirement、actual state/history/Git audit等を既にbindingする。derived provenance/semantic検証結果は同factsから決定的に導出し、新しい保存field・hash projection/version・readiness/action/diagnostic enumを追加しない。v1/unsupported tokenの暗黙upgrade禁止、stale hash/action拒否は不変。公開Recovery executor未releaseの時点でのformal correctionであり、旧6A実装の一律blocked判定を正しい新contractとして流用しない。

6C開始時には本節に従ってSnapshot/ID audit/純粋classifierをfact-basedに更新し、既存code-only blocked shortcutがCase Cを消さないことをregressionで固定してからexecutorへ接続する。通常APIのguardやvalidatorを弱めず、public skip/force flagを作らない。このDesign Follow-upではruntime/source/testsを変更しない。6Eのforward writerも既存file順/消費前置/lag確認を守り、6Dのpost-decision exact target要件を本例外で緩めない。

### Recovery ownership・retirement（DG-03、H-01修正）

通常のwithCanonicalGateは現契約のまま例外時releaseを行う。Transactionは同じcommon gateの明示lifecycleを使い、Receipt以後の未完了時にfinallyで無条件releaseしない。nested取得、別canonical lock、clientのretain/skip flagは禁止。以下のownership archiveとephemeral barrierを混同しない。

#### Durable archiveとbarrier

ownershipの正本はstaging/recovery-ownership/{transaction_id}/配下のimmutable archive。anchor、claims、retiring、retiredはv1で削除・GC・上書き禁止。ephemeralなstaging/.fn004-recovery.lockはMutexBarrierであり、ownerの正本でもmutable headでもない。削除できるのは下記のretirement手順に従うbarrierと検証済みtemp/backupだけである。

| artifact | path / identity | Git / policy |
| --- | --- | --- |
| MutexAnchor | recovery-ownership/{tx}/anchor.json | runtime-local、永久保持。1 txに1 anchor/mutex_id |
| MutexClaim | 同txのclaims/{sequence}.json | runtime-local、永久保持。正整数sequence、no-clobber |
| MutexRetiring | 同txのretirements/{owner_sequence}.retiring.json | runtime-local、永久保持。owner_sequence=0はanchor、以後claim sequence |
| MutexRetired | 同txのretirements/{owner_sequence}.retired.json | runtime-local、永久保持。対応retiringを参照 |
| MutexBarrier | staging/.fn004-recovery.lock | runtime-local ephemeral exclusion marker。owner履歴は置かない |

archive表のpathはstaging/基準。filename数値部分はjournalと同じpadStart(6)規則だがretirementでは000000を許す。anchor/claim sequenceを再利用しない。tx/MutexID/Bindingの付替え、新しいmutex_idで同txをやり直すこと、閉じたlineageをsequence=0で再開することは禁止。別txの新Recoveryは別anchorとUUIDを使う。13f75bb時点の未merge・未実装layout（anchor自体を.lockへ置く形式）を新layoutへ黙って読み替えない。旧kindがbarrier pathにあればGATE_CORRUPTでSTOP。現在productionにこれらのartifactはなく、Slice 1〜5のschemaやbootstrapを移行しない。

MutexAnchorPayload={mutex_id:UUID, binding:Binding, gate:GateWitness|null, owner:ProcessOwner, operator:Actor, predecessor_exit:ExitProof|null, observed_state_hash:Hash, acquired_at:Timestamp}。

MutexClaimPayload={mutex_id:UUID, binding:Binding, sequence:正safe integer, previous_claim_hash:Hash, owner:ProcessOwner, operator:Actor, gate:GateWitness|null, predecessor_exit:ExitProof, observed_state_hash:Hash, acquired_at:Timestamp}。

両payloadのfield/hash projectionは元draftから不変。operatorはtrusted local_process actor、Binding.actorは元Receiptのまま。anchorのgateは初回に採用するcanonical gate（存在すれば元Owner.gate）、predecessor_exitはそのeffective ownerの終了証明。gate=nullは全terminal proof/completionがvalidでcanonical gate不在のcleanupだけ。anchor.predecessor_exit=nullは移管元owner自体がない初回terminal cleanupだけで、claim.predecessor_exitはgate不在でも直前ownerの終了証明を必須とする。unfinished workでcanonical gateが失われていればSTOP。

MutexProof={anchor:MutexAnchor, claims:MutexClaim[]}。これはjournalに保存する当時のownership prefixであり、現在headやretirementを証明するmutable viewではない。現在のrunはarchive全体を別途検証する。sequence=1のpreviousはanchor.hash、以後直前claim.hash、欠番/fork/別Binding/異mutex IDは禁止。predecessor_exit.ownerは直前ownerと全field一致、checked_at<=acquired_at、取得時刻は非減少。全entryを読み数値順で検証し、listing順・cache・PID大小でheadを選ばない。

#### 新しいclosed schemas

追加artifactも全object closed、全field required、明示したunionだけnullable。各rootは{schema_version:1,kind:下記literal,payload:完全型,hash:Hash}。HashProjectionV1={schema_version,kind,payload}、hash=H(projection)。既存JCS/SHA、immutable/no-clobber、同identity同全内容は元record、異内容はINTEGRITY_CONFLICT、publication phase/published/temp保持の規則を使う。別Ownerの内容へ同pathを再公開しない。

| artifact | kind |
| --- | --- |
| MutexBarrier | "fn004-recovery-barrier" |
| MutexRetiring | "fn004-recovery-retiring" |
| MutexRetired | "fn004-recovery-retired" |

OwnershipRef={sequence:非負safe integer, owner_hash:Hash}。0のhashはanchor.hash、n>0はclaim[n].hash。

MutexBarrierPayload={binding:Binding, mutex_id:UUID, anchor_hash:Hash, barrier_id:UUID}。

BarrierWitness={artifact:MutexBarrier, byte_length:非負safe integer, sha256:Hash, device:Decimal, inode:Decimal}。同bytesのstrict parse/JCS＋LF、BHashとdev/inoを検証する。barrier_idは一度生成し、残存barrierを作り直さない。retirementに記録済みIDを再利用しない。

MutexRetiringPayload={binding:Binding, mutex_id:UUID, owner:OwnershipRef, barrier:BarrierWitness, canonical_gate:GateWitness, terminal_proof_hash:Hash, completion_hash:Hash, terminal_journal:JournalRef|null, final_manifest_hash:Hash, terminal_state_hash:Hash, retiring_at:Timestamp}。

retiring.ownerは現在head、全Binding/MutexIDはanchor/claimと一致。barrierのanchor_hashは同anchor.hash、barrier.bindingも一致。proof/completionは当該Requestの元immutable record、terminal_journalは元proofの末尾（receipt-onlyだけnull）。manifest/state hashはそのterminal proofと、cleanup時の実canonical/state全内容一致を検証した値。cleanup中のunknown外部変更はSTOP。canonical_gateは現在runが所有する同common gateの実witness。retired.ownerは対応retiring.ownerと一致、retiring_hashはそのhash、retired_at>=retiring_at。1 ownerに各1 recordだけ、retired単独/ownerなし/別hash/別barrier/別repositoryは不正。

retiring/retiredはjournal phaseではない。Journal、Terminal Proof、Completion、History、ID stateへowner追記やgeneration更新を行わない。retirement recordをHistory成功扱いにもしない。

#### Owner/headとretirementの決定算法

1. anchorと全claimのschema/hash/filename/chainを検証し、head=最大sequence（claimなしは0）。全retirement recordも検証し、owner refがこのchainに存在することを要求する。存在しない未来owner、重複、未知file、partial、gap/fork、不正hashはSTOP。
2. headにretiringがなければACTIVE、retiringだけならRETIRING、対応retiredまであればRETIRED。これらはownership内部のderived stateで、新readinessではない。retirementをfile absenceから推定しない。
3. RETIREDでも同barrierが残る間、元ownerにはbarrier/自己の検証済みpublisher tempを解放するrelease-only authorityだけが残る。domain write、追加journal、同ownerの再executionは不可。外部RecoveryはそのownerがliveならGATE_BUSYでactionなし。
4. headがRETIREDでそのbarrierが存在せず、terminal proof/completion整合・未知残存物なしならlineageはSEALED。current ownerはなし（ObservedEvidence.effective_owner=null、owner_status="none"）、latest historical ownerはheadのまま。新anchor/claim/barrierをこのtxへ作らない。別txの新barrierは旧retiring.barrierとID/Bindingが異なるので、旧ownerが削除してはならない。
5. ACTIVE/RETIRINGでbarrierがない、またはRETIREDなのに当該canonical gateが残る等、手順と一致しない状態は自動再作成せずSTOP。barrierが残るhead ownerの終了を証明できれば、次の唯一のsequenceへsuccessorを公開できる。古いretirementだけで新headをretired扱いしない。
6. crashした旧ownerのretiringが未完でも、終了証明付きsuccessorがあれば旧ownerはSUPERSEDED。旧retiredを捏造して埋めず、旧recordを残す。現在判断は新headとそのretirementだけで行う。旧未完recordの参照/内容検証は省略しない。

successorは前ownerがRETIREDでも、barrierが残る限りOS終了証明を必須とする。生きたprocessからの自動handoffはv1で提供しない。CLI-only Recoveryに対する保守的な制約であり、PID/時間だけのretirementではない。SEALED後は通常利用のために過去processの終了を待たず、新txの通常gate取得を許せる（他の全runtime guardは必要）。

#### 初回取得・successor・common gate

新規Recoveryは全対象evidenceと他unfinished workを検証し、必要な元owner終了を実probeする。候補anchor全内容を固定してhashを計算し、その参照を持つbarrierをexclusiveに完成公開/syncする。barrier取得前後に同txの既存archiveと他active Recoveryを再検査する。別BindingのbarrierはBUSY、不正ならGATE_CORRUPT。既存archiveを別anchorで上書きしない。

初回barrierだけではcanonical/state mutation authorityを得ない。exclusive publisherが保持する内部の初回構築capabilityで、同hashのanchorをarchiveへno-clobber公開/syncして初めてanchor ownerになる。barrier→anchor間crashでarchiveがない/不完全ならmanual STOP。他processが不存在から候補anchorを再生成して採用することは禁止。この保守的なpublication窓を通常gateのstale削除で救済しない。

既存barrierの引継ぎはarchiveのhead ownerの終了証明→次sequenceの唯一のpathへno-clobber claim→全chain/head/barrier再検証。二者が同headを見れば同pathを競合する。敗者はleaseを得ず、勝者のbarrier/recordを削除せず再inspectする。全publisher tempも発見し、未解決publicationを古いprefixへ戻して扱わない。

自動終了証明は同一Linux host/boot/PID namespace、非nullのstart identity/process_instance_id、移管前後のPID不存在確認が必要。PIDが存在し同startならlive、別startならPID再利用でSTOP。別host/boot/namespace、null、probeアクセス不能もSTOP。saved ExitProofやkill(pid,0)だけで権限を作らない。

head確定後、現在barrierのinode/全bytesとarchive head/process所有を確認した内部live capabilityからcommon canonical gateを採用する。既存gateのmetadataは変更せず、dev/ino/全bytesを保持する。terminal cleanupでgate不在なら、同common lockのwx primitiveをRecovery内部contextで一度取得する。自己barrierの存在を認めるのは検証済みhead capabilityだけで、public skip optionや別canonical lockではない。新しいgateはoperation="recovery_cleanup"、全process identityを現在ownerへbindingする。unfinished workにこの不在例外を使わない。

各write/releaseは最新archive head、current process、現在barrier、同common gateの所有を再確認する。通常のnormal acquisitionはbarrierとactive/retiring archiveを取得前後に検査し、未解決ならBUSY/RECOVERY_REQUIREDで止める。archiveがあるだけで永久blockせず、SEALEDを完全検証したものだけ通常利用へ戻す。これらの実装は6C/Eで、6Aや現Slice 2をdocsだけで変更しない。

#### cleanupとretirementの順序

cleanupを実行できるのは、現在のclaimed ownerが、元terminal journal/proof/completion/History/state/canonicalの整合を検証し、same common gateを所有している場合だけ。finish_terminalは既に確定したterminal stateからproof/completionを完成するまでで、retirementのためにstateを再加算しない。各run actionのterminalization後は次の共通epilogueを使う。新しいpublic actionは追加しない。

1. owner/head/barrier/terminal整合を確認し、許可済みbackup/temp/restore/既知publisher tempだけを検証してcleanup・directory sync。ownership archive、元Owner/input/intent/journal/proof/completion/Historyは消さない。未知fileはsweepせずSTOP。
2. cleanup対象がなく、semantic結果が不変であることを再確認して、current ownerのMutexRetiringをdurable公開する。以後はrelease-onlyで、新たなdomain writeをしない。
3. retiringにbindingしたcanonical gateの所有を照合してreleaseし、directory sync・不在確認する。release失敗/結果不明なら先へ進まずbarrierと全archiveを保持する。
4. 同barrier/head所有を再検証してMutexRetiredをdurable公開する。canonical gateが解放済みであることをrecordで証明する。元Timestamp/全内容を保存し、同record再送で新しい時刻を生成しない。
5. 自己の完成・同内容publisher tempだけを再照合して片付け、現在headとretired/retiring/barrierの一致を確認し、当該barrierのdev/ino/全bytesを再確認してunlink・directory sync。**anchor、claim、retirement recordsは一切削除しない。**
6. SEALEDを再観測して終了。barrier unlink後sync failureも元typed errorを保持し、成功を偽装しない。process memoryのretired boolをproofとして使わない。

crash後の別ownerは既存retiring/retiredを書き換えず、barrierが残る限り終了証明と次claimを使い、自分のretiring/retiredを新しく公開してreleaseする。canonical gateが既に不在でも、その状態だけでretiredと断定しない。terminal proofがvalidなcleanupに限り新ownerがcleanup用common gateを取得し、同じepilogueで閉じる。旧ownerは終了済みなので後からbarrierを削除できない。旧capabilityの再利用は失敗させる。

cleanup failureはsemantic Transaction failureではない。terminalがvalidで既知cleanup/retirement/barrier解放だけが残るならcleanup_required。live ownerなら外部actionなし、終了証明可能ならcleanup action。非terminal/証拠不足はrecovery_required、hash/lineage矛盾はblockedまたは元typed error。retiring/retiredのschema/hash/owner参照不正はGATE_CORRUPT、同identity異内容のpublishはINTEGRITY_CONFLICT、観測変化はRECOVERY_REQUIRED。新readiness/error enumは作らない。

#### H-01反例の閉鎖とcrash matrix

旧13f75bbの「Bが末尾claimを削除→anchorだけ残る」は本契約では禁止操作。Bがどの地点でcrashしてもBのclaimは残り、Cはhead=B以降を見て、live Bなら拒否、終了を証明できれば次sequenceだけを公開する。retirementが不足してもheadを縮めない。claimを削除する正常cleanup経路はなく、no-clobber pathが残り続けるため同sequenceの別owner再公開は成立しない。

| crash / race地点 | 残存根拠と次の判定 |
| --- | --- |
| barrier取得前 | 新ownerなし。元gate/ownerを再検証。既存live ownerならBUSY |
| barrier公開途中 | completed markerまたはpartial/temp。partial/未anchorはSTOP、削除で不存在にしない |
| barrier後・anchor前 | unanchored barrier。manual STOP。owner/anchorを推測生成しない |
| canonical gate取得後・claim前 | successorの新gate取得は順序違反で到達不可。検出したらSTOP |
| successor公開途中 | 唯一の次pathとtempを全検証。部分/競合/不明publicationならSTOP |
| successor後・gate前 | 新headが残る。liveならBUSY、deadならn+1へ進むだけ |
| gate取得後・cleanup前 | head＋barrier＋live gate。dead takeoverは全3者の照合後 |
| cleanup途中 | terminal結果不変、head残存。known残存物だけ再cleanup、unknownはSTOP |
| cleanup完了・retiring前 | headはACTIVEのまま。dead successorが再検証し自分のretiringを作る |
| retiring公開途中 | 既存完全record/tempを照合。不明ならSTOP、ownerをretiredにしない |
| retiring後・gate release前 | RETIRING＋同gate。owner deadなら次claimでcleanup継続 |
| gate release後・retired前 | gate不在でもRETIRING。次ownerはterminal cleanupとして新common gateを取得 |
| retired公開途中 | 完全retiredまたは未完。未完からretirement成功を推測しない |
| retired後・barrier unlink前 | RETIREDだがrelease-only ownerを保持。liveなら拒否、deadならn+1 cleanup |
| barrier削除/sync途中 | 永久archiveのhead/retiredは残る。同barrierが残れば上行、不在かつ全terminal整合ならSEALED。sync error自体は伝播 |
| process exit直前/再送 | SEALEDならactionなし。残存barrierがあれば最新ownerの終了を確認し次claimのみ |
| parallel Recovery | 同次sequenceのno-clobber競合。一人だけowner、敗者のbarrier削除は禁止 |

publication済みrecordが不正/欠損、fork/gap/重複、退行した観測head、retirement without owner、retired without retiring、hash mismatch、unknown schema、PID曖昧、他Bindingのbarrier、concurrent head change、old observationは自動mutation禁止。既知の参照/観測headやjournal内MutexProofより短いarchiveも拒否する。通常runtimeでは全publicationを永久保持し、プロトコル外の削除・Git/FS全巻戻し・flushを無視するstorageまでローカルhashで検出できるとは主張しない。これらは既存v1保証範囲外で、認識した不足は常にfail-closedとする。

#### restart / clone / historical proof

process restartは同working treeの永久archive＋barrierを読み、同host/boot/namespaceの実終了証明でのみclaimを進める。machine restartでboot identityが変わった未完了ownershipはmanual STOP。SEALEDな過去archiveはprocessの生死と独立して履歴として検証する。後続の正当なTransaction後は過去retirementのmanifest/stateを現在値と一致要求せず、immutable terminal proofと元recordの整合を検証する。現在値との一致は未完了/cleanup中にだけ要求する。

archive/barrierはruntime-localでGitへ持ち運ばない。Terminal Proof内のMutexProofは当時のprefix snapshotであり、fresh cloneが元working treeのlatest owner/retirementを知った証拠ではない。fresh cloneはGit-managed terminal proof/History/stateの過去整合を読めるが、runtime archive不在から旧txのsequenceを0へ戻したり元Recoveryを自動再開したりしない。旧txのRecoveryに必要なarchive/owner/gateがないならSTOP。別の新txも、単一authoritative working tree・bootstrap/History/state・Invalidation/Receipt等の既存guardを満たす場合だけで、clone flagによるbypassはない。既存Terminal Proof/Journal/Completionを書き換えてretirementを補わない。

6Aはarchive/barrier/retirementのclosed schema、hash/projection、immutable chain/discovery、pure ownership state/classificationを実装できる。claim/adoption/retirement/cleanupのruntime実行は6C以降。6Aのcanonical/ID/state/History/dispatch/CLI禁止範囲は不変。

### Recovery inspect / runとpure decision（DG-05）

inspectはreadonly。lock・mutex・domain artifact・cacheを作成/修復/削除せず、common gateの強制取得もしない。同じ安全pathで全対象listing/bytes、全14 canonical、History/state/proofs、gate/mutex、OS owner、固定Git audit identityを二度収集する。同じhash/listingでもreservationではなくbest-effort観測。差があればracedとしてactionなし。runは後述の排他下で全て再検証する。

ObservedEvidenceの完全schema：

~~~text
{
  repository_instance_id: RepositoryID,
  bootstrap_hash: Hash,
  transaction_id: TransactionID,
  request_id: RequestID,
  files: [{path: ObservedPath, kind: "file"|"directory"|"missing"|"symlink"|"other",
           byte_length: nonnegative safe integer|null, sha256: Hash|null}],
  canonical_manifest: Manifest|null,
  state_hash: Hash|null,
  history_head_hash: Hash|null,
  git_audit: GitAuditIdentity|null,
  historical_maxima: NamespaceMap|null,
  journal_head: JournalRef|null,
  journal_phase: Phase|null,
  terminal_proof_hash: Hash|null,
  completion_hash: Hash|null,
  effective_owner: ProcessOwner|null,
  owner_status: "live"|"exited"|"unverifiable"|"none",
  input_revalidation: "valid"|"stale"|"unavailable",
  consistency: "stable"|"raced"
}
~~~

filesは発見した全entryと期待する固定必須pathの不在をpath ASCII順uniqueで含む。regular fileだけlength/hash非null、他は両方null。全manifest/各hashは実bytesから検証する。不正JSON/domain schema/unsupported version等で検証不能な対応summaryはnull、元codeをdiagnosticsへ残す。input_revalidationは元Plan/Decision/store/candidate/rulesと実snapshotを既存domain validatorで評価した内部結果で、caller提供boolではない。証明不能をvalidにしない。exact field setは表示用API実装名を指定するものではない。

ObservationHashProjectionV2は正確に次のobject。observed_state_hash=H(projection)。これは未実装draftのobservation v1を置き換えるversion 2で、保存済みSlice 1〜5 artifact/hashは変更しない。

~~~text
{
  schema_version: 2,
  kind: "fn004-recovery-observation",
  binding: Binding,
  requests: [{request_id: RequestID, receipt_hash: Hash}],
  evidence: ObservedEvidence（filesだけ下記AuthoritativeFilesへ置換）
}
~~~

requestsはrepository全体のstrict/static検証済みRequestをrequest_id ASCII順uniqueで列挙し、元ReceiptHashProjectionV1から計算する。AuthoritativeFilesは収集したfilesからlatest cacheのtransaction.jsonと保存Request envelopeのraw file entryだけを除いたarray。processingを含むraw Request hashの代わりにrequests/Bindingのimmutable Receipt hashを使う。derived view/cacheをauthorityへ昇格させない。除外したcache/Requestもschema/bindingは検証し、未知/破損を黙認しない。診断可能な不正ならactionなし、read/path/I/O failureなら元typed errorをthrowする。

hashは全archive anchor/claim/retiring/retired/barrier、journal head、全14 canonical relevant bytes、state、History、Terminal Proof/completion、参照Plan/Decision/Approval/Invalidation/candidateと実owner-probe結果をbindingする。全repositoryの既知artifact・期待不在pathも収集し、対象txだけのfilterで他unfinished workを隠さない。ownership head/retirementは全record setから導出し、advisoryなhead fileを設けない。時刻取得値、mtime、message、cache内容はhashへ足さない。git_audit/historical_maximaは完全監査結果、取得不能なら両方null・manual STOP。runはGit最新性/completenessを別途再検証し、hashだけで証明した扱いにしない。

inspect resultの完全schema：

~~~text
{
  schema_version: 2,
  binding: Binding,
  evidence: ObservedEvidence,
  observed_state_hash: Hash,
  classification: "active"|"abortable"|"rollbackable"|"decidable_success"|
                  "finalizable"|"terminal_incomplete"|"cleanup_only"|
                  "terminal"|"manual_stop",
  allowed_actions: ("abort"|"rollback"|"finalize_success"|"finish_terminal"|"cleanup")[],
  readiness: "initialized"|"cleanup_required"|"recovery_required"|"blocked",
  diagnostics: [{code: ExistingCode}]
}
~~~

#### Terminal evidence優先・排他的なaction契約（M-01訂正）

以下は実装上のif文の推奨順ではなく、pure classifierの正式semanticsである。全候補artifactをstrict検証してから、対象transactionの進行段階を一つ確定し、その段階内でactionを一つ以下に決める。欠損/矛盾を低い段階へfallbackして救済しない。runの所有権取得は別の必須条件であり、分類自体はmutationしない。pure classifierは検証済み同一snapshotとtrusted owner-probe/元入力再検証結果だけを入力とし、時計・FS・OS・Git操作、listing順、cache、現在時刻を判定根拠にしない。

本節のreceipt-onlyは「durable Receiptがあるがjournal entryが一度も公開されていない経路」をいう。ReceiptだけでOwnerがない受付直後の不明状態もこの観測familyに含むが、abort可能なのはvalid Ownerがある場合だけ。合法なreceipt-only ABORTEDは、全14 canonical=Owner.original、state=Owner.before全内容、pending=null、ID未消費、当該successful Historyなし、canonical置換なしである。journal=[]、intent=null、consumed_state=null、after_state=before_state、phase=ABORTED、history=nullをproofに要求する。未実行の再dispatch、rollback、成功の意味を持たない。実canonical/stateの元値との一致は未完了terminalization/cleanup時の条件であり、後続の正当な編集後に過去SEALED proofを無効化しない既存のhistorical validation境界は維持する。

**検証・段階決定の優先規則**：

1. 全schema/hash/identity、全journal/ownership chain、元Receipt/Plan/Approval、actual canonical/state/Historyを検証する。canonicalは前述のbyte provenanceとsemantic validityを分けて検証し、Case Cの候補事実は保持するが、terminal/success優先を確認するまでrollback例外を確定しない。Completionとproofの不整合、ABORTED/ROLLED_BACKと当該HistoryまたはCOMMIT_DECIDEDの共存、unknown bytes/partial/unsupported/欠落必須参照はmanual_stopでactionなし。Completionはproofが公開済みの場合だけ合法。Completionだけあってproofがない状態は不足を補う通常caseではなくintegrity conflictである。
2. valid Completion＋そのexact proofがあれば、semantic terminalization完了。proofのphaseにかかわらずabort/rollback/finalize_success/finish_terminalへ戻らない。残存cleanup/ownership retirementだけを分類する。
3. Completionがなく、valid公開proof、または下記の完成proof publication intent、またはvalid terminal journal/stateがあれば、terminal_incomplete。receipt-onlyでもfinish_terminalだけを候補とし、pre-terminal actionを選ばない。
4. 上記terminal証拠がなく、COMMIT_DECIDED/HISTORY_COMMITTEDまたはそのresumeがあれば、元成功方針のforward completionだけ。successful Historyがあれば元decision/exact record/許可state lagを要求し、不足はSTOP。Historyを無視してabort/rollbackへ落とさず、Historyだけから欠損decisionを捏造しない。
5. terminal証拠も成功方針もないCOMMITTING/ROLLING_BACKは既存のactual original/target、消費、rollback方針、入力再検証でrollbackまたは正式all-target例外のfinalize_successに分割する。
6. 上記すべてがなく、valid Owner＋journalなし、またはPREPARING/PREPAREDで下記abort predicateを満たす場合だけabort。それ以外はmanual_stop。

この段階の意味は一方向である。proof公開後は「abort前」へ、Completion公開後は「terminalization未完」へ、retirement後は「semantic操作が必要」へ戻らない。公開証跡の欠損を認識した場合は退行でなくSTOP。完全なartifact集合全体を巻き戻す外部操作まで検出する保証は追加しない。

**完成publication intentと再利用**：独立した新artifact/schemaは追加しない。既存publisherの正規tempが完全なTerminalProofArtifactとしてstrict検証でき、同固定target path/identity・元terminal事実との一致・durabilityを検証できる場合だけ、完成proof publication intentとして扱う。未知/partial/unreadable tempはSTOP。複数temp/公開proofが同identityで異なるJCS全内容ならINTEGRITY_CONFLICT、同内容なら同一publicationであり一件に畳み込む（未知tempをskipしない）。完成tempだけではterminal証明公開完了とはみなさず、finish_terminalで元内容を公開する。検証不能なsync/publication結果から新しいproofを作り直さない。

公開proofのidentityは固定tx path＋Binding＋hashであり、元Owner、terminal authority、ended_at、diagnostics、inputs、phase、state、manifestを全内容保持する。新Recovery ownerへの継承でproof.authorityや時刻を現在ownerへ置き換えない。現在run authorityはDG-03の独立archive/common gateで証明する。公開proofがあれば再生成禁止。proofも完成intentもないことを検証した場合だけ、元terminal journal、または一度目のreceipt-only abortから既存DG-04規則で最初のproofを構築できる。

**actionのclosed predicatesと許可publication**（すべて上記validation・stage partitionを満たし、他unfinished workなし）：

COMMITTINGのoriginal/target判定は全14 manifestとchanged_pathsで行い、全targetと「全targetでないoriginal/mixed」を分離する。no-opはoriginal==target・changed_paths=[]なので特別に、実state=beforeかつ未消費ならrollback（state不変）、実consumedなら入力valid/rollback方針なしで正式例外のfinalize_success、入力staleで安全復元可能ならrollback、入力unavailable/証拠不足ならSTOPとする。変更あり全targetなのに未消費stateなら置換前消費契約との矛盾でSTOP。全target成功例外が成立するcaseへoriginal側rollback predicateを重ねない。

外部inspectは、進行段階を確定しても、必要なeffective ownerがliveならactive/[]、終了証明不能・観測race・所有不明ならmanual_stop/[]にする。必要gate消失を通常取得で救済しない。DG-03のgate不在例外はproof＋Completionがvalidなterminal cleanupだけで、proof-only finish_terminalへ拡張しない。取得済み本人live capabilityに限る既存内部context以外にself/bypass optionはない。

出力classificationはpredicateから固定する：abort=abortable、rollback=rollbackable、finish_terminal=terminal_incomplete、cleanup=cleanup_only。finalize_successはCOMMITTINGの正式all-target例外ならdecidable_success、元COMMIT_DECIDED/HISTORY_COMMITTEDならfinalizable。不要はterminal、live owner等の実行中阻害はactive、証明不能/矛盾/未知はmanual_stop。allowed_actionsは対応する1 actionだけ、terminal/active/manual_stopは[]。readiness/diagnosticsは既存優先規則と下記mappingから導出する。receipt-only finish_terminalのrun outcomeは元proof.phase=ABORTEDに対応するabortedであり、成功resultを返さない。

**exactly-one property**：Completion有無、terminal evidence有無、成功方針有無で段階を分割するため、cleanupとfinish_terminal、両者とabort/rollback/finalize_successは交差しない。pre-terminalではjournal phaseと全target判定/入力validityで分割する。複数段階の矛盾した証拠はvalidation failureとしてSTOPし、priorityで片方を隠さない。validで安定した同一snapshotからは、所有権guard適用後に単一action、不要、またはmanual STOPだけを返す。未知組合せのdefaultはmanual_stop/[]。fully clean/SEALEDはterminal/[]で第6actionを作らない。

### 6Aの実装境界と検証契約

6Aは本節の全新artifact validator/projection、archive/retirement chain/discovery、pure Recovery分類、owned immutable publisher/cache primitiveを実装できる。publisherはschema/fixture foundationであり、claim/adoption/retirementのruntime serviceを公開しない。TerminalProofの保存publisherはモデル/fixtureとして検証し、実stateからterminal証明を生成するserviceは6C/D。ownership archive/barrier/retirement schema・chain・derived stateのpure検証は6A、実OS probe・claim取得・retirement・cleanup・lease採用/保持は6C。whole targetとHistory builderは6B、成功publisherは6D、normal orchestration/readiness接続は6E、公開CLIは6F。

canonical/state mutation、ID消費、restore/forward実行、History公開、initial dispatch、公開CLIは6Aで禁止。通常readerのpresence guard/success-only proofをこの段階で解除しない。

必須negative vectorsは全required/null/unknown/version、duplicate JSON、不正path、同ID異内容、seq gap/fork、genesis previous不一致、時刻変更、owner/binding不一致、partial末尾/cache破損、no-op分類、success後rollback、rollback方針後success、state二重消費、未消費rollback、消費後rollback→次success、proof package不足、old inspect token、二重Recovery successor競合、owner null/PID再利用/別host、claim/retirementの欠損/異owner/異hash、H-01の各crash点、SEALED後の再claim禁止、fresh cloneでの旧lineage再開拒否、advisory cache変化とimmutable Receipt変化のobservation区別を含む。filesystem/clock/probeはtrusted test seamで分離し、6A pure classifierは同一snapshotで同一actionを返す。failure injectionはpublisherの各sync境界から導入し、client/環境変数のvalidation bypassを設けない。
