# FN-005 楽曲一覧データ生成機能

> 2026-11-25 運用切替：実装済み。loadSongTablesはFN-004非依存の全14表検証後に6表を投影します。公開JSON契約・生成規則は維持します。

## 目的・適用範囲と実装状態

canonical CSVからSCR-003向けの静的JSONを生成・検証する。CLI・公開JSON・契約テストとSCR-003への接続を実装済み。初期G00001はcanonicalから90作品・120音源を生成する（今回確認時点）。

[PR #100](https://github.com/YutoSuga/helloproject-song-data/pull/100)で承認された[公開JSON契約](../screens/public/SCR-003-公開JSON設計.md)をキー・型・必須性・null許容・導出・順序の正本として維持する。本書は生成機能の責務と受入条件を定め、新しいJSON契約を作らない。canonical schemaは[データ仕様](../data/データ仕様.md)に従う。

## 責務境界

| 担当 | 責務 |
| --- | --- |
| FN-001 | 作家ランキング集計・ランキングJSON生成。楽曲一覧生成を含めない |
| FN-005 | 楽曲CSV結合・対象抽出・導出・公開JSON生成と検証。ランキングを集計しない |
| FN-004 | 人間が確定した入力のcanonical CSVへの安全な反映。公開JSON生成は含めない |
| SCR-003 | JSON読込・最低限形式確認・ブラウザ内検索/並び替え・一覧/音源詳細・読込エラー表示 |
| [共通ビルド](../system/公開サイトデータ生成・ビルド仕様.md) | 各生成処理の呼出、Git管理JSONの整合性検査、CIと公開 |

## 入力・関連付け・対象artist

入力は`data/`のartists.csv、works.csv、songs.csv、song_artists.csv、creators.csv、song_creators.csv。結合キーと対象集合は公開JSON契約の「結合・対象範囲」に従う。初期対象はG00001（Juice=Juice）。指定artistがprimaryのsongだけを対象にし、featuredだけのsongを含めない。multiple-primaryでも指定artistがprimaryなら含む。

対象songからworkへ関連付け、1 workにつき1行とする。同workの他artistだけのsongは詳細・検索・日付に混ぜない。creatorは対象songのsong_creatorsから取得し、正規名はcreators、掲載名義・role・順序はsong_creatorsを使う。作詞・作曲・編曲に加え既存の特殊roleも保持し、workに直接creditを割り当てない。releases/release_tracksを一覧・日付導出に使わない。

## JSON構造・作品と音源

全キー・型・必須性と例は[公開JSON契約のパス別定義](../screens/public/SCR-003-公開JSON設計.md#パス別定義)を参照する。rootにschema_version・artist・works、work内にsongs、song内にcreditsを持つ。表の`credits[].creator_id/name`は`creator_id`と`creator_name`の略記であり、`name`キーを新設しない。表でnull許容とした値もキーは出力し、任意CSV空欄をnull、空リストを[]とする。

代表タイトルはworks.titleをそのまま使用し、最古songのtitleやID順から選ばない。音源名はsongs.titleを保持する。Version違いは同work配下の別songとして保持し、version_name・version_typeと音源別credit差分を失わない。同一音源の再収録はcanonical上の同じsongであり商品数だけ増やさない。

## 日付・順序・重複・欠損

導出と生成配列順は公開JSON契約を正本とする。対象primary songの既知release_date最小値を作品日付とし、全欠落はnull。一部欠落を仮日付で補わない。date_incompleteは内部管理用で表示条件には使わない。

対象song_id・work_id・検索名集合を契約に従って重複排除する。creditのIDとroleを保持し、共同担当やVersion差分を統合して消さない。canonicalの重複キー違反は正常な重複排除で隠さず検証エラーとする。

worksはwork_id ASCII順、songsは日付昇順・不明末尾・song_id順、creditsはrole ASCII順・credit_order数値（不明末尾）・creator_id順。search_creator_namesは文字列を重複排除し、ロケール非依存のJavaScript文字列比較（UTF-16コード単位）昇順に固定する。

## 出力単位・再現性と検証

出力はartistごとに`site/data/songs/<artist_id>.json`、schema_versionは1。一覧用と詳細用に分割せず、作品・対象音源・creditを一つのJSONに含める。ランキングとは独立した派生物である。

同じcanonical入力とartist指定で同じJSONを再生成できること。実行時刻や環境に依存する値を加えない。生成側で必須値・型・PK/FK・既存enum・日付・対象集合・導出値・配列構造・出力形式を検証する。必須列欠落、未知artist/enum、参照切れ、不正日付等は生成失敗とし、黙った除外やcredit_nameの推測補完をしない。正常な対象0件はworks=[]とする。欠損許容値と不整合を区別する。

失敗を共通ビルドへ伝達し、検証不合格のJSONを公開対象としない。診断は問題のCSV・キー・項目を特定できるものとする。CLIは成功0・検証/入出力/引数エラー1。検証完了後に出力先と同じディレクトリのUUID付き一時ファイルへ排他的に書き、renameで置き換える。一時ファイルはfinallyで削除する。検証失敗時に既存JSONを上書きしない。

## CLI・共通ビルドとの接続

`npm run songs:generate -- [G00001]`（scripts/generate-songs.js）で単独生成、`npm run songs:validate -- [G00001]`（scripts/validate-songs.js）で生成済みJSONの厳密契約・画面の消費形式・canonical再生成結果とのバイト一致を検証する。位置引数はartist_idを最大1個、既定G00001。未知引数・存在しないartistは失敗する。

`site:build`はランキング→楽曲の順に独立CLIを実行し、一方の非0終了で失敗する。読み込みはsrc/song-catalog.jsから既存withCanonicalRead・strict CSV parser・canonicalValueError/schemaを再利用する。6入力表のヘッダ（空表を含む）、必須値・PK/FK・enum・日付・順序を検証し、schemaやFN-004実装を変更しない。song_artists.credit_orderは正式データ仕様のsong単位一意性を適用する。全体validatorの既知D1との差異はFN-004変更として扱わない。

検索・ソート用の派生JSONを都度生成する方式は採らない。SCR-003がロード済みworksをブラウザ内で検索・3順序へ並び替える。NFKC/空白AND、日本語Collator、日付null末尾は[画面仕様](../screens/public/SCR-003-楽曲一覧・検索.md#検索並び替え確定仕様)を正本とする。

## テスト・受入条件

- primary/featured/multiple-primary、同work他artist除外、複数Versionと異なるcredit、共同担当・特殊roleで対象集合を確認する。
- 既知/一部欠落/全欠落日付、null・空配列、代表タイトル、安定順・重複排除を確認する。
- 必須値・FK・enum・日付・重複キーの異常を生成側で検出し、失敗を伝達する。
- schema_version・全必須キー・型・null許容・enum・入れ子配列が既存公開JSON契約と画面利用に一致することをCIで検証する。
- 同じ入力の再生成一致、commit済みJSON差分検出、既存ランキングへの影響なしを確認する。
- 画面側は検索/並び替え/詳細と読込異常を別途検証し、CSV検証を重複実装しない。

自動テストはtest/song-catalog.test.js・test/song-catalog-model.test.js・test/generated-data.test.js、任意のブラウザ検証はscripts/check-song-catalog.cjs。実測結果は[実装検証記録](../../history/reviews/song-catalog-validation.md)に記載する。
